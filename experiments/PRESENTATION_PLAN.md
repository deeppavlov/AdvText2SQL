# Презентация AutoText2SQL — план и сценарий

**Длительность**: 15-20 минут (можно сжать до 10)
**Аудитория**: научный руководитель + комиссия DeepPavlov
**Стиль**: научный, конкретные числа, честная интерпретация
**Слайды**: 14

---

## Слайд 1. Титульный

**Заголовок**: AutoText2SQL — автоматизированное создание Text2SQL-инструментов под конкретную БД
**Подзаголовок**: От разведки схемы до production-сервиса в одном CLI
**Имя, лаборатория, дата**

**Скажи**: «Сегодня я расскажу про систему, которая принимает на вход URL произвольной PostgreSQL-БД и за ~30 минут разворачивает специализированный Text2SQL-инструмент, заточенный именно под эту БД».

---

## Слайд 2. Проблема: универсальные Text2SQL не знают вашу БД

**Содержимое**:
- Универсальные модели (gpt-3.5/4) обучены на BIRD/Spider/WikiSQL — но не на ВАШЕЙ БД
- Проблемы в проде:
  - Галлюцинации имён колонок («WHERE customer_name» вместо «WHERE client_full_name»)
  - Неправильные JOIN-связи между таблицами
  - Игнорирование domain-специфики (формат дат, бизнес-правила, enum-значения)
- **Сделать модель под каждую БД вручную = недели работы**

**Скажи**: «Когда универсальный Text2SQL встречает реальную банковскую БД с 100+ колонок типа TEXT и кучей legacy-полей, он галлюцинирует. Альтернатива — обучить под каждую БД отдельно — требует человеческой разметки, что дорого и не масштабируется».

---

## Слайд 3. Идея: автономный пайплайн

**Диаграмма** (одна горизонтальная стрелка через 5 коробок):
```
[ PROFILE ] → [ GENERATE ] → [ VALIDATE ] → [ FINE-TUNE ] → [ SERVE ]
   (DB)        (LLM synth)    (exec filter)   (LoRA)         (MCP/vLLM)
```

**Скажи**: «Каждый этап автоматический, читает артефакт предыдущего, пишет следующий. Нет ручного шага. Пользователь даёт URL — получает рабочий сервис».

---

## Слайд 4. Архитектура — что под капотом

**Содержимое — таблица**:
| Модуль | Файл | Что делает |
|---|---|---|
| profiler/ | DBConnector, SchemaExtractor, StatsCollector | вычитывает метаданные БД |
| synth/ | LLMSyntheticGenerator + TemplateSyntheticGenerator | генерит Q-SQL пары |
| synth/Validator | execution + parse + whitelist | фильтрует невалидное |
| training/ | DatasetBuilder + notebook_generator | chat-format JSONL для FT |
| serve/ | Dockerfile.vllm + Text2SQLClient | production-сервис |
| heal/ | HealCollector + HealSQLGenerator | self-healing loop |

**Скажи**: «6 модулей, ~5k строк кода, 35 unit-тестов. Все модули coupled через файлы на диске — это даёт идемпотентность и независимый дебаг каждой стадии».

## Слайд 5. Стадия 1: Profiler — что мы знаем про БД

**Картинка**: пример `profile.json` (фрагмент)

**Содержимое**:
- Структура: таблицы, колонки, типы, FK
- Статистика колонок:
  - numeric: min/max/avg/median
  - categorical: top-5 значений + частоты
  - date: диапазон
- 3 sample-строки на таблицу
- low-cardinality values (enum)

**Скажи**: «Это полный слепок БД за ~30 секунд для card_games. ~120 SELECT-запросов к системным таблицам и колонкам. Дальше БД не нужна — генерация работает только с profile.json».

---

## Слайд 6. Стадия 2: Генерация — два пути

**Содержимое**:

**Template-генератор** (25 SQL-шаблонов):
- 100% валидный SQL (нет галлюцинаций)
- Бесплатно
- Ограниченное семантическое разнообразие

**LLM-генератор** (gpt-4/4o/codex):
- Естественные вопросы
- Сложные конструкции (CTE, окна, подзапросы)
- Стоит денег + нужна валидация

**Стратегия**: используем оба + объединяем

**Скажи**: «Template даёт надёжный фундамент, LLM — разнообразие. На выходе ~1000 пар на эксперимент, после фильтрации остаётся ~85-95%».

---

## Слайд 7. Стадия 3: Валидация — три уровня защиты

**Диаграмма потока**:
```
raw.jsonl → check_parse (sqlglot) → check_whitelist (SELECT only)
         → check_execute (на реальной БД)
         → check_LLM_judge (опц.)
         → validated.jsonl + rejected.jsonl
```

**Содержимое**:
- Parse: SQL разбирается как PostgreSQL
- Whitelist: только SELECT, без DROP/DELETE/UPDATE
- Execute: реально выполняется на БД, должен вернуть ≥1 строку
- Judge: GPT-4 проверяет соответствие вопрос ↔ SQL

**Скажи**: «Execution filter — это наша главная гарантия от ошибочных примеров. SQL, который не запустится на реальной БД, в обучении не участвует».

---

## Слайд 8. Стадия 4: Fine-tuning — LoRA на Qwen-Coder-7B

**Содержимое — таблица**:
| Параметр | Значение |
|---|---|
| База | Qwen2.5-Coder-7B-Instruct (4-bit) |
| Метод | LoRA |
| r / α | 16 / 32 |
| lr | 2e-4 |
| epochs | 1 |
| batch × grad_accum | 1 × 8 |
| max_seq_length | 12288 (фикс баг с 4096) |
| Target modules | q/k/v/o/gate/up/down_proj |

**Инфраструктура**: Colab A100 40GB, unsloth (2× ускорение)
**Время**: ~40 мин на одну модель

**Скажи**: «Системный промпт со схемой БД ~10k токенов — на 4096 контексте ответ обрезался. Подняли до 12288 — обучение работает корректно».

---

## Слайд 9. Стадия 5: Production-обёртка

**Содержимое**:
- vLLM в Docker с LoRA hot-swap (без merge)
- MCP-сервер (FastMCP) для AI-агентов
- Python SDK: `Text2SQLClient(api_url).query(question)`
- QueryLogger → `queries.jsonl` + `failed.jsonl` для self-healing
- Хот-старт через `profile.json`: <50 мс вместо 30+ сек

**Скажи**: «Все артефакты на диске, инвариант train==inference поддержан через единый системный промпт».

## Слайд 10. Эксперимент: какая модель-генератор лучше?

**Содержимое**:
- Тестовая БД: card_games (6 таблиц, 115 колонок)
- Тест: BIRD card_games subset, 31 реальный вопрос

- Базовая модель FT: Qwen-Coder-7B
- 5 генераторов синтетики:
  - gpt-4.1 (топ)

  - gpt-4.1-mini

**Скажи**: «Главный вопрос — нужна ли сильная и дорогая модель для генерации синтетики, или хватает дешёвой?».

## Слайд 11. Главная таблица результатов

**Содержимое** (3 итерации эксперимента):
| Генератор | Эксп. 1 (RU) | Эксп. 2 (RU+EN) | Эксп. 3 (EN) |
|---|---|---|---|
| baseline (без FT)      | 19.4% | 19.4% | 32.3% |
| gpt-4.1                | 22.6% | **39.4%** | 32.3% |
| gpt-4o-mini            | 12.9% | 29.0% | 25.8% |
| gpt-5.1-codex-mini     | 19.4% | 22.6% | 25.8% |
| gpt-4.1-mini           |  6.5% | 19.4% | — |
| gpt-4.1-nano           | 16.1% | 16.1% | **35.5%** |

**Точка отсчёта**: Classical full-BIRD FT (Эксп. 0) = 38.7%

**Скажи**: «Лучший результат — Эксп. 2 с gpt-4.1 = 39.4% — **обходит** classical full-BIRD FT при 10× меньше данных и без человеческой разметки».

---

## Слайд 12. Что мы узнали — 5 ключевых выводов

1. **Автономный пайплайн на синтетике сравнялся с classical full-BIRD FT** (39.4% vs 38.7%) при 10× меньше данных
2. **Языковой инвариант train↔test критичен**: моно-RU обучение не переносится на EN-тест (Эксп. 1 → 2: +17 п.п. от добавления EN-синтетики)
3. **Evidence в инференсе — самостоятельный мощный рычаг**: baseline 19.4% → 32.3% БЕЗ всякого FT
4. **На сильном baseline дешёвая nano парадоксально лучше**: 35.5% против 32.3% у топ-модели — её «прямой» SQL ближе к BIRD-стилю
5. **Эксп. 1 не «провал», а методологическая находка** — фиксирует языковой рассинхрон как явление

**Скажи**: «Третий вывод важен для практики: иногда грамотный промпт даёт больше чем дорогое обучение».

## Слайд 13. Сравнение с классическим подходом

**Содержимое** — таблица:
| | Classical FT (Эксп. 0) | AutoText2SQL (Эксп. 2) |
|---|---|---|
| Train data | ~10k человеческих пар | 1000 синтетических |
| Разметка | да, ручная | нет, автогенерация |
| Применимость | только под BIRD-БД | под любую PG-БД |
| Время с нуля | дни-недели разметки | ~30 минут |
| Accuracy | 38.7% | 39.4% |

**Главный месседж**: автономный подход **не уступает** классическому, при этом **снимает зависимость от человеческой разметки** и **переносится** на новые БД.

**Скажи**: «Это и есть scientific contribution проекта — мы показали, что для одной БД синтетика может полностью заменить размеченные данные».

## Заготовки ответов на вероятные вопросы

| Вопрос | Ответ |
|---|---|
| «А почему именно Qwen-Coder?» | Сильный на коде, есть unsloth-патчи, в 4-bit влезает в A100 40GB |
| «Сколько стоит сгенерировать 1000 пар?» | ~$3-5 на gpt-4.1, ~$0.20 на gpt-4o-mini |
| «А что если БД 1000 таблиц?» | complexity_score адаптивно растит target_count; profile.json остаётся читаемым; expect ~5000 пар |
| «BIRD evaluation — это достаточный тест?» | Это стандартный бенчмарк, 31 вопрос для card_games — мало для статистики, но достаточно для смежного сравнения генераторов |
| «А private-данные не утекают в gpt-4?» | LLM получает ТОЛЬКО метаданные (имена, типы, top-N значений). Если low-cardinality колонки содержат PII — добавить redact на этапе профайла (TODO) |
| «Почему language=ru работает хуже?» | Test (BIRD) на английском. Промпт-домейн модели нужно совмещать с test-домейном. Установили это как закон в Эксп. 1→2 |
| «gpt-3.5 без FT в Эксп. 0 = 27.4%, а ваш baseline 19.4% — почему?» | Разные модели: Эксп. 0 baseline — gpt-3.5-turbo через API; наш baseline — Qwen-Coder-7B локально (для честного сравнения с FT-версиями той же базы) |
| «Self-healing уже работает?» | Реализован сборщик failed-queries + GPT-4 корректор, не интегрирован в продакшн-цикл (требует деплоя сервиса в прод) |
| «А почему MCP, а не просто HTTP?» | MCP — стандарт для AI-агентов (Claude, GPT). HTTP тоже есть (vLLM OpenAI-compatible). MCP даёт интеграцию с LLM-агентами «из коробки» |

## Демо-сценарий (если успеваем 2-3 мин в живую)

```bash
# 1. Профайл новой БД (~30 сек)
text2sql profile --db-url postgresql://.../chinook

# 2. Генерация (~3 мин)
text2sql generate --profile data/profiles/chinook/profile.json \
    --count 500 --generator both --language en

# 3. Подготовка датасета (мгновенно)
text2sql build-dataset --profile ... --synthetic ...

# 4. Показать что готово к Colab
ls data/finetune/chinook/
```

Если демо не успевает — заранее заскриншоть выводы и покажи их.

## Финальный месседж для конца презентации

> «AutoText2SQL показал, что для отдельной БД можно полностью заменить человеческую разметку автоматически сгенерированной синтетикой — и при этом **не потерять качества** по сравнению с классическим подходом. Это снимает главный барьер промышленного применения Text2SQL: необходимость размечать данные под каждую новую БД».
