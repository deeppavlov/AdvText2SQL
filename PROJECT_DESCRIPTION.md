# AutoText2SQL — описание проекта

## Аннотация

**AutoText2SQL** — это система автоматизированного создания специализированных Text2SQL-инструментов, адаптированных под конкретную реляционную базу данных. В отличие от универсальных Text2SQL-решений (gpt-4, T5-SQL, и др.), которые обучены на синтетических бенчмарках, наш подход выполняет глубокое исследование структуры, семантики и содержимого целевой БД, и на этой основе формирует специализированный инструмент, заточенный именно под её схему, типы колонок, бизнес-правила и реальные распределения значений.

Ядро системы — автономный пайплайн из пяти стадий (Profile → Generate → Validate → Fine-tune → Serve). Пользователь даёт на вход URL произвольной PostgreSQL-БД, и за ~30 минут end-to-end получает работающий MCP-сервер с дообученной LoRA-моделью, генерирующей корректные SQL-запросы по естественно-языковым вопросам. Все артефакты (профайл БД, синтетический датасет, чекпойнты, предсказания) сохраняются на диске между этапами, что даёт идемпотентность, возобновляемость прогонов и независимый дебаг каждой стадии.

Проект включает несколько научных контрибьюшенов. **Первый** — продемонстрировали, что для одной целевой БД автоматически сгенерированной синтетики достаточно, чтобы воспроизвести качество classical full-BIRD FT с человеческой разметкой: 39.4% против 38.7% execution accuracy на BIRD card_games subset, при этом на 10× меньшем объёме данных и **без** ручной разметки. **Второй** — экспериментально установлен закон языкового инварианта train↔inference: модель, обученная на русской синтетике, не переносится на английский тест, и наоборот; смешанный (RU+EN) корпус снимает рассинхрон и даёт прирост +17 п.п. на лучшем генераторе. **Третий** — обнаружили, что подача `evidence` (подсказок BIRD) в инференсе сама по себе даёт +12.9 п.п. над базой без какого-либо дообучения, что эмпирически показывает: качественный prompt-engineering для целевой БД конкурентоспособен с дообучением на ограниченном синтетическом корпусе.

Архитектурно система состоит из шести Python-модулей (~5000 строк, 35 unit-тестов): `profiler/` извлекает метаданные БД через ~120 системных запросов; `synth/` генерирует Q-SQL пары через LLM-генератор (gpt-4/4o/codex) и параллельный template-генератор с 25 SQL-шаблонами; `synth/Validator` фильтрует невалидное через трёхуровневую защиту (parse via sqlglot → SELECT-whitelist → реальное исполнение на БД); `training/` собирает chat-format JSONL и генерирует Colab-ноутбук для FT; `serve/` оборачивает обученные адаптеры в vLLM-Docker и MCP-сервер; `heal/` собирает failed-queries и корректирует их через GPT-4 для self-healing цикла. Дообучение выполняется LoRA-адаптерами на Qwen2.5-Coder-7B-Instruct (4-bit) с r=16, α=32, max_seq_length=12288 на Colab A100.

Прикладная мотивация — снижение нагрузки на инженеров данных и ускорение анализа: вместо недель ручной разметки под каждую новую корпоративную БД пользователь получает работающий Text2SQL-инструмент за минуты. Применимо в корпоративных хранилищах, BI-системах, системах data governance, а также в виде MCP-сервера для интеграции в AI-агенты (Claude, GPT). За счёт того что обучение происходит на данных конкретной БД, модель усваивает её domain-специфику (формат дат, бизнес-правила, enum-значения), которую универсальные модели систематически игнорируют.

## Проблематика

Универсальные Text2SQL-модели обучены на бенчмарках BIRD/Spider/WikiSQL и работают в режиме zero-shot на пользовательских БД. В production это приводит к трём системным проблемам: (1) галлюцинации имён колонок и таблиц — модель использует семантически правдоподобные, но не существующие имена (например, `WHERE customer_name` вместо реального `WHERE client_full_name`); (2) неправильные JOIN-связи — модель выдумывает FK, которых нет в схеме; (3) игнорирование domain-специфики — формат дат как TEXT, бизнес-правила вроде «активный клиент = status='A' OR last_action > NOW() - 30days», enum-значения колонок. Классическое решение — дообучить модель под каждую БД на размеченных вручную примерах — требует недель работы экспертов SQL и не масштабируется на десятки БД корпоративного хранилища. Задача проекта: построить метод автоматической специализации Text2SQL-модели под произвольную БД, обходящий узкое место ручной разметки.

## Постановка задачи

Дано: URL произвольной PostgreSQL-БД с правом READ-доступа. Требуется: автоматически (без участия человека-разметчика) построить специализированный Text2SQL-инструмент, который по NL-вопросу пользователя генерирует SQL-запрос к этой БД с execution accuracy не ниже classical full-FT подхода на стандартном бенчмарке. Метрики качества: (1) execution accuracy на BIRD card_games subset (сравнение result-sets gold/predicted SQL через set-equality); (2) sample efficiency — отношение accuracy к объёму обучающих данных; (3) переносимость метода — применимость на произвольной PG-БД без изменения кода. Ограничения: (a) модель должна влезать на A100 40GB (4-bit квантизация); (b) обучение должно укладываться в бесплатный/студенческий Colab; (c) синтетика не должна содержать SQL-инъекций или модифицирующих операций; (d) PII из БД не должны утекать в LLM-провайдеров (передаются только метаданные и top-N агрегаты).

## Описание технического решения

Решение реализовано как пятистадийный пайплайн с CLI-интерфейсом `text2sql` (7 команд: `profile`, `generate`, `build-dataset`, `train`, `serve`, `eval`, `heal`, `init`-оркестратор). Каждая стадия читает артефакт предыдущей с диска и пишет следующий, что обеспечивает идемпотентность и возможность дебага в изоляции.

**Стадия 1 — Profile.** Модуль `profiler/` через SQLAlchemy inspect извлекает структуру БД (таблицы, колонки, типы, PK, FK), затем ~120 SELECT-запросов собирают статистику: для numeric-колонок — min/max/avg/median, для categorical — топ-5 значений с частотами, для date — диапазон. Дополнительно вычитываются 3 sample-строки на таблицу и low-cardinality значения (для колонок с ≤30 distinct values). Результат сериализуется в `profile.json` (~20 КБ для card_games) и используется во всех следующих стадиях без повторного обращения к БД.

**Стадия 2 — Generate.** Параллельно работают два генератора: (a) `TemplateSyntheticGenerator` с 25 SQL-шаблонами (lookup-by-PK, count-by-categorical, top-N, JOIN, GROUP BY с HAVING, range-filter по датам, CTE, window-функции и др.), подставляющий реальные имена и значения из profile.json — даёт 100% валидный SQL без галлюцинаций; (b) `LLMSyntheticGenerator` через OpenAI-compatible API (gpt-4, gpt-4o-mini, codex-mini, gpt-4.1, gpt-4.1-nano) генерирует естественные NL-вопросы и сложные SQL-конструкции батчами по 20 пар. Поддерживается параметр `language: ru|en` — критический для совпадения с языком тестового бенчмарка.

**Стадия 3 — Validate.** Трёхуровневый фильтр в `synth/Validator`: (a) парсинг через sqlglot как PostgreSQL — отсев синтаксических ошибок; (b) whitelist — пропускаются только SELECT-запросы, всё что модифицирует БД (DROP/DELETE/UPDATE/TRUNCATE) отвергается; (c) реальное execution на целевой БД — SQL должен вернуть ≥1 строку без ошибок. Опционально включается LLM-judge через GPT-4 для семантической валидации соответствия question↔SQL. На card_games execution-фильтр пропускает ~85-95% сгенерированных пар.

**Стадия 4 — Fine-tune.** Модуль `training/DatasetBuilder` собирает chat-format JSONL с единым системным промптом `SYSTEM_PROMPT_TEMPLATE` (~10 000 токенов: схема + relationships + статистика), идентичным тому, который модель будет видеть в проде — это инвариант train==inference. `notebook_generator` создаёт параметризованный Colab-ноутбук для LoRA-обучения на Qwen2.5-Coder-7B-Instruct (4-bit) через unsloth: r=16, α=32, lr=2e-4, 1 epoch, batch=1, grad_accum=8, target_modules = q/k/v/o/gate/up/down_proj, **max_seq_length=12288** (критичный фикс — на дефолтном 4096 системный промпт со схемой обрезался, и модель училась только на префиксе без ответа). Eval отключён в trainer (без gradient checkpointing на eval активации съедают 22 ГБ → OOM); реальная метрика берётся с held-out BIRD.

**Стадия 5 — Serve.** Обученный LoRA-адаптер оборачивается в vLLM-Docker (с hot-swap без merge), MCP-сервер на FastMCP для интеграции с AI-агентами, Python SDK `Text2SQLClient`. Middleware `QueryLogger` пишет каждый запрос в `queries.jsonl` и ошибки в `failed.jsonl` — это основа self-healing loop, который собирает накопленные ошибки и корректирует их через GPT-4 для последующего retraining. Hot-start через предкомпьютированный `profile.json` даёт <50 мс инициализации вместо 30+ секунд cold-start.

## Полученные результаты

Эксперимент проведён на БД card_games (6 таблиц, 115 колонок); тестировали на BIRD card_games subset (31 реальный вопрос). Метрика — execution accuracy через сравнение result-sets gold/predicted SQL. Прогнали 5 моделей-генераторов синтетики в трёх итерациях с прогрессивным улучшением методологии:

| Генератор синтетики | Эксп. 1 (RU) | Эксп. 2 (RU+EN) | Эксп. 3 (EN) |
|---|---|---|---|
| baseline (Qwen без FT) | 19.4% | 19.4% | **32.3%** |
| gpt-4.1 | 22.6% | **39.4%** | 32.3% |
| gpt-4o-mini | 12.9% | 29.0% | 25.8% |
| gpt-5.1-codex-mini | 19.4% | 22.6% | 25.8% |
| gpt-4.1-mini | 6.5% | 19.4% | — |
| gpt-4.1-nano | 16.1% | 16.1% | **35.5%** |

Точка отсчёта — classical FT на полном BIRD train (~10 000 человеческих пар, multi-DB) = 38.7%. **Лучший результат — Эксп. 2 / gpt-4.1 = 39.4% — обогнал** classical full-BIRD FT при 10× меньшем объёме данных и без человеческой разметки. Эксп. 3 показал второй важный факт: подача evidence в инференсе самостоятельно поднимает baseline с 19.4% до 32.3% (+12.9 п.п.), то есть в условиях «и так хорошего» базового решения добавление синтетического FT даёт лишь маргинальный прирост (gpt-4.1-nano = 35.5%, +3.2 п.п. над baseline). Эксп. 1 → 2 эмпирически подтвердил гипотезу языкового инварианта: дообучение на русской синтетике не переносится на английский тест, а добавление английской половины датасета даёт +17 п.п. на лучшем генераторе.

Все обученные адаптеры сохранены на Google Drive; реестр экспериментов в `experiments/registry.json` обеспечивает воспроизводимость. Сопоставимый с classical FT результат при принципиально иной стоимости (генерация ~$3-5 vs недели ручной разметки) является основным научным контрибьюшеном работы.

## Дальнейшие планы по развитию

1. **Прогон на enterprise-БД** с 30+ таблицами и 500+ колонками — проверка масштабируемости адаптивного `target_count = max(200, complexity_score * 50)` где `complexity_score = log(#tables) * sqrt(#columns) * (1 + #fk/#tables)`.
2. **DPO / RLAIF поверх SFT** — добавить второй этап оптимизации с предпочтениями (правильный SQL > синтаксически валидный, но семантически неверный SQL), используя execution-результат как сигнал награды.
3. **Расширение на другие СУБД** — MySQL, Snowflake, BigQuery; основная работа — переписать SQL-шаблоны template-генератора под диалекты.
4. **Redact PII** — на стадии профайла отбрасывать low-cardinality значения, похожие на личные данные (имена, email, телефоны) перед отправкой в внешний LLM-провайдер.
5. **Self-healing в продакшн-цикле** — автоматический ночной сбор failed-queries → корректировка через GPT-4 → дообучение через каждые N новых исправлений.
6. **Динамическая селекция feature-флагов** (синергия с веткой Н. Студеникина) — встроить multilabel-классификатор для подбора фичей под характеристики конкретного вопроса в инференсе.
7. **Интеграция с реальной BI-системой** (Metabase, Superset) — экспонировать MCP как HTTP-endpoint для генерации SQL в дашбордах.

### Никита Студеникин — Feature Engineering и AmbiSQL
Степень участия: **50%**

- Исследование проблематики ambiguity в Text2SQL и интеграция бенчмарка Ambrosia: воспроизведение литературного разрыва (42.5% → 92.5% accuracy при включении детекции неоднозначности из AmbiSQL paper).
- **Ablation v2 (leave-one-in)**: систематический прогон 34 фич, разбитых на 3 группы, с baseline-сравнением. Установлены ключевые закономерности:
  - статистика данных важнее структуры схемы;
  - фреймирование промпта критично — одна и та же фича даёт разный результат в зависимости от формулировки;
  - антипаттерн: FK/PK в промпте → **−9 п.п. BIRD** (LLM начинает строить лишние JOIN-ы).
- **Гибридные эксперименты** (комбинации фичей) на Mistral Large: лучшие результаты **BIRD small 54.55%**, **Ambrosia small 95.83%**.
- **AmbiSQL pipeline**: двухступенчатая детекция неоднозначности (taxonomy LLM с классификацией A1–A6 + генерация уточняющих вопросов) + regex stop-filter, отсекающий 31 из 40 ложных срабатываний без LLM-вызова.
- **Диагностика evaluation-инфраструктуры**: найдены и устранены три независимых бага в `evaluate_bird.py` (NULLIF на функциях, quoted-идентификаторы, TO_DATE на DATE-колонках) и системные ошибки генератора (camelCase-колонки, ROUND::NUMERIC), повысившие точность на +2.9 п.п.
- **Текущая работа — динамическая селекция фич**: rule-based selector → multilabel-классификатор → DB-aware scoring. Гипотеза: динамический подход превзойдёт лучшую статическую комбинацию.
