# Phase 2, шаг 1 — multilabel-разметка полезности

**Выполнено 29.10.2026.** Подготовлена разметка для первого multilabel-классификатора
по сохранённым ответам DeepSeek. Классификатор ещё не обучен. LoRA остаётся отдельной
работой Ильи; этот этап её не требует и не изменяет.

Датасет — [data/multilabel_utility/deepseek_20261029](../data/multilabel_utility/deepseek_20261029/summary.md).
Сборка — [build_multilabel_dataset.py](../scripts/build_multilabel_dataset.py),
политика меток — [multilabel_targets.py](../scripts/multilabel_targets.py).
Результат [rule-based selector](06_rule_selector.md) сохранён; его правила не подстраивались.

## Источники и проверки

| Параметр | Значение |
| --- | --- |
| Модель | DeepSeek Flash; точная модель, заявленная версия и API-параметры в manifest |
| Одиночная серия | Baseline + 33 флага, 68 завершённых запусков |
| Комбинации | 2+35, 14+35, 14+32+35 и 1+14+32+35, восемь запусков |
| Вопросы | BIRD 241 + Ambrosia 227 = **468**, 60 БД |
| Наблюдения источников | **76 запусков**, 334 файла с проверкой SHA-256 |
| Выходы классификатора | **16** допустимых механизмов; все 33 флага сохранены для аудита |
| Условные пары | Пять сравнений × 468 вопросов = **2 340** записей |
| Новые платные запросы / подключения к БД | **0 / 0** |

Проверяются сохранённые протоколы и разрешённые I/O-ревизии, точная маска флагов,
модель и параметры, hashes датасетов, статус запусков и соответствие SQL сохранённым
score. Реализация фичей и evaluator должны соответствовать историческому протоколу.
Существующий датасет Phase 0.2 проверяется и используется как источник входов и splits.
Small не добавляется повторно. Результаты Mistral/GPT с DeepSeek не смешиваются.

## Значение меток

Одиночные фичи сравниваются **только с baseline, в котором все FEAT=false**.
Фича 35 здесь отдельный предсказываемый выход, а не незаметно включённая основа.
Полезность зависит от этого контекста. Перенос меток на фон 35 или на модель Ильи
требует отдельной проверки.

| Сохранённый результат | Utility | Benefit target | Loss mask | Preference target / mask |
| --- | ---: | ---: | --- | --- |
| Фича верна, baseline неверен | +1 | 1 | true | 1 / true |
| Фича неверна, baseline верен | −1 | 0 | true | 0 / true |
| Оба верны | 0 | 0 | true | null / false |
| Оба неверны | 0 | 0 | true | null / false |
| Наблюдение отсутствует или невалидно | null | null | false | null / false |
| Механизм исключён политикой | Сырой utility сохранён при наличии наблюдений | null | false | null / false |

`benefit_target=0` на ничьей означает **нет наблюдаемого улучшения в этом проходе**,
а не доказанную бесполезность фичи. Второй вариант `preference_targets` позволяет
учиться только на различиях качества, маскируя ничьи. Выбор схемы loss/весов и
порогов относится к следующему шагу и должен делаться на train/dev.

Метрики Ambrosia пересчитаны строго: `error` не считается правильным отрицательным
ответом. Ошибки выполнения SQL модели BIRD — наблюдаемый неуспех; ошибки эталона
и нераспознанные ошибки оценщика маскируются. Наличие корректного ответа в прогоне
само по себе не превращается в положительную метку полезности.

У **FEAT_25 / Ambrosia, question_id=278** в checkpoint сохранена пустая строка.
Она помечена `invalid_prediction=true`, `observed=false`, `correct=null`;
соответствующая метка исключена из loss. Пустой ответ не засчитан как успешная
детекция отсутствия неоднозначности. Исходные checkpoint/report не переписывались.

## Какие фичи доступны

Порядок 16 выходов зафиксирован в manifest:
**1, 2, 12, 13, 14, 15, 16, 20, 21, 23, 25, 28, 29, 30, 32, 35**.

Это механически допустимые одиночные переключатели. Их включение не доказывает,
что механизм изменил контекст каждого вопроса или реально сработал на нём.

| Исключённые флаги | Причина |
| --- | --- |
| 3, 4, 7 | В одиночных прогонах не включён родитель 2 |
| 27 | Feedback требует повторов, но 17 выключен |
| 33 | Не включён родитель 32 |
| 34 | Не включены 32 и 33 |
| 36 | Не включён родитель 15 |
| 8, 9, 10, 11, 17, 18, 19 | Инфраструктура и повторы; не question-level targets первого классификатора |
| 5 | Флаг не меняет fallback light-схемы в текущей реализации |
| 6 | Консервативное исключение после ранее обнаруженной неполной подготовки схем BIRD; нужен исправленный повтор |
| 26 | Состояние кэша зависит от истории; этой истории нет в модельных входах |

Сырые наблюдения исключённых флагов сохранены. Их случайные отличия от baseline
не используются как доказательство полезности неработающего механизма.

## Условная полезность

| Фича | Контекст / контроль | С чем сравнивается |
| --- | --- | --- |
| 2 | 35 | 2+35 против 35 |
| 35 | 2 | 2+35 против 2 |
| 14 | 35 | 14+35 против 35 |
| 32 | 14+35 | 14+32+35 против 14+35 |
| 1 | 14+32+35 | 1+14+32+35 против 14+32+35 |

У каждой пары проверяется, что маски различаются ровно заявленной фичей.
Эти 2 340 записей находятся в `conditional_labels.jsonl` и **не подмешиваются**
в одиночные targets: например, 32 на all-false фоне и 32 поверх 14+35 — разные
наблюдения. Это те же 468 вопросов, а не новые независимые обучающие примеры.

## Состав и дисбаланс

| Часть | BIRD | Ambrosia | Вопросов | Доступных benefit targets | Положительных | Различий качества |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| Train | 131 | 136 | 267 | 4 271 | 117 | 187 |
| Dev | 55 | 46 | 101 | 1 616 | 57 | 102 |
| Test | 55 | 45 | 100 | 1 600 | 40 | 66 |
| Всего | 241 | 227 | **468** | **7 487** | **214** | **355** |

Различия качества — число пар «вопрос × фича» с utility ±1, а не число уникальных
вопросов. Полная таблица +/−/ничьих для каждого флага — в [summary.md](../data/multilabel_utility/deepseek_20261029/summary.md).

Положительных меток лишь около **2,86%**. В train для отдельных фичей всего
1–3 положительных наблюдения. Предсказание всех нулей даст высокую обычную
accuracy и не решит задачу. При обучении нужны учёт дисбаланса, masked loss,
сравнение с постоянными решениями и проверка downstream качества.

## Входы и разделение

Модель получает только `inputs = {question, evidence, schema_stats}`. Эталонный SQL,
ответы модели, difficulty, benchmark, DB ID, split и семейства находятся вне inputs.
В `examples.jsonl` экспортированы ID для сопоставления, inputs и целевые векторы;
идентификатор не должен попадать в текст или признаки классификатора.

`splits.json`, `cv_folds.json`, `ambrosia_family_holdout.json` скопированы побайтно
из Phase 0.2. Проверяются соответствие всех ID, входов и групп исходным записям,
отсутствие пересечений БД/семейств и только train внутри четырёх CV-fold.

Test **уже просмотрен при проверке rule-based selector**. Он сохранён как
ретроспективная диагностика; для финальных выводов потребуются новые вопросы/БД
и контроль пересечений с обучением модели Ильи. Флаги возможного совпадения с
примерами промптов перенесены из Phase 0.2.

## Ограничения и следующий шаг

Это слабые метки из одного прохода каждой конфигурации. Повторных измерений нет,
поэтому случайное изменение ответа не отделено от причинного эффекта фичи.
Датасет не задаёт оптимальную совместную маску: улучшения отдельных переключателей
нельзя складывать. Произвольных комбинаций для честного offline replay пока нет.
Точные токены отдельных вопросов неизвестны и не выдумываются.

**Шаг 1 подготовки данных завершён. Следующий — реализация классификатора**:
замороженный энкодер вопроса/evidence, признаки схемы и выходы по выбранным
механизмам, с маскированной функцией потерь. LoRA энкодера пока не нужна.
После него — ограничения сочетаний, интеграция и ручная проверка итогового
пайплайна. Даже при хороших multilabel-метриках прирост SQL/F1 не гарантирован.

## Воспроизведение

```powershell
.venv\Scripts\python.exe scripts/build_multilabel_dataset.py
.venv\Scripts\python.exe scripts/build_multilabel_dataset.py --verify-only
```

Повторная команда проверяет существующий bundle. Она не перезаписывает готовую
разметку при изменении источников/политики: для новой версии нужен новый `--out`.
Старые feature_labels, датасет Phase 0.2 и исходные результаты остаются неизменными.

Проверки: **78 офлайн-тестов**, Ruff, отдельный `--verify-only` и независимая
повторная сборка во временную папку. Все девять файлов bundle совпали побайтно;
хеши 334 файлов источников и прежние splits не изменились.
