## Checkpoint и исторические прогоны

`query_checkpoint.json` — основной атомарно сохраняемый файл с хешами идентичности и ответов.
`query_results.json` остаётся совместимым экспортом. Старый плоский файл без идентичности
не принимается автоматически: нужен новый выходной каталог. Совпадения одних ID недостаточно.

Сначала сохраняется основной checkpoint, затем экспорт. Если запись экспорта прервана,
ответ остаётся в основном файле; продолжение требует явного восстановления экспорта из
его поля `predictions`. Несогласованность не исправляется молча и не вызывает повторную генерацию.
Содержимое ключей API и паролей в checkpoint не записывается.

Изменились генерация SQL и fingerprints кода. Для следующих экспериментов нужен новый
протокол и отдельный каталог. Старые манифесты не обновляются задним числом; запуск старой
серии на новом коде должен отклоняться проверкой хешей. Совместимость результатов старого
и нового генератора не утверждается. Для AUD-002 нельзя получить новые ответы простой
переразметкой старых меток.

## Статический pipeline остаётся опорой

До контрольного измерения исправленная версия считается кандидатом, а не подтверждённой
заменой статического pipeline. Результаты классификатора не заменяют статический контроль.

| Зафиксированный контроль | Фичи и промпт | Подтверждённый исторический full |
| --- | --- | --- |
| BIRD | 2+7+14+32+35, SQL MIPRO seed 43 без демонстраций | 132/241, EX 54,77% |
| Ambrosia | 14+32, исходные SQL/taxonomy промпты | 171/211, Acc 81,04%; F1 60,78%; recall 49,21% |

Источники: [BIRD full](23_bird_prompt_full.md), [Ambrosia full](24_ambrosia_prompt_full.md).
Это метрики прежней версии, а не измерения после исправлений аудита.

Приоритет перед дальнейшим переобучением классификатора — проверка сохранения качества:

1. На сохранённых предсказаниях отдельно проверить изменение оценки из-за перевода
   эталонов/evaluator. Это отделяет изменения измерителя от изменений генерации.
2. Проверить исправленный статический генератор с теми же моделью, промптами,
   конфигурациями и фиксированными ID. Учесть вариативность LLM; разобрать парные
   исправления/ухудшения, ошибки SQL, детектора и инфраструктуры.
3. Перед принятием версии подтвердить full-метрики на тех же 241/211 вопросах как
   регрессионный контроль, без подбора фичей/промптов по full-ошибкам. Не менять знаменатель
   ради сохранения процента; необходимые исправления эталонов оформить отдельной версией.
4. При падении выяснить причину; исправленный код не объявлять равным опоре только на
   основании unit-тестов. Классификатор сравнивать с согласованным статическим контролем.

Платные измерения по этому протоколу пока не выполнялись; сохранение прежних процентов
после аудита ещё не подтверждено. Исторические ответы, манифесты и метрики остаются неизменными.
Ручные команды и порядок сравнения A/B/C подготовлены в
[отдельном протоколе регрессионного контроля](29_static_pipeline_regression.md).

## Воспроизводимость: два разных действия

| Действие | Что требуется | Что проверяется |
| --- | --- | --- |
| Обучение на сохранённом комплекте | Отслеживаемые файлы `data/configuration_utility` и `data/multilabel_utility`, Python-зависимости; для настоящего обучения — подготовленный encoder | Все хеши выходных файлов, соответствие меток исходным наблюдениям внутри комплекта, derivations, DB/family splits и folds. В model metadata записывается `training_bundle` |
| Полное восстановление происхождения меток | Дополнительно архивы исходных запусков/ответов и соответствующая историческая версия исходников | Полная проверка `source_files_sha256`; режим builders `--verify-only` остаётся строгим и ничего не пропускает при отсутствии архива |

Это явное разделение обязанностей, а не автоматическое отключение проверок при отсутствии
файлов. При необходимости Python API `load_rows(..., verify_sources=True)` включает полный аудит.
В `.gitattributes` для обоих каталогов обучающих комплектов закреплены переводы строк LF:
автоматическая замена на CRLF в Windows checkout больше не нарушает сохранённые хеши.
Сохранённые версии v1 и v2 не смешиваются; проверка чистого комплекта здесь относится к v1
`data/multilabel_utility/deepseek_20261029`, а не к новым незакоммиченным данным классификатора.

Пример проверки обучения из чистого checkout после установки зависимостей проекта и
`requirements-classifier.txt` (без encoder download, API и SSH):

```bash
python scripts/train_multilabel_classifier.py train --dry-run
```

Для новых запусков используются отслеживаемые `local/*.sh` и `scripts/*.py`; `.env` с
реквизитами остаётся локальным. Например, просмотр доступных параметров не требует соединений:

```bash
bash local/run_prompt_comparison_durable.sh --help
```

## Проверки и границы результата

- Ruff прошёл на изменённых Python-модулях.
- Основная регрессия: 269 тестов и 90 subtests прошли.
- `tests/test_prompt_comparison.py` отдельно: 9 тестов и 8 subtests прошли, включая
  настоящие GEPA, TextGrad и MIPRO с подменённым provider и запрещённой сетью. В основной
  серии этот один smoke исключён: старый пилот GEPA и новое сравнение закрепляют разные
  версии библиотеки, которым нужны отдельные процессы. Восемь остальных тестов повторяются;
  всего уникальных тестов — 270.
- Проверка чистого комплекта сделана в отдельном каталоге `.cache/` без `.ps1` и архивов
  запусков, с установленными локальными Python-зависимостями. Установка зависимостей с нуля
  и настоящая PostgreSQL в эту проверку не входили.
- Перевод всех эталонов SQLite в PostgreSQL и равенство результатов на двух СУБД ещё
  требуют отдельной верификации. Успешный AST-разбор сам по себе этого не доказывает.
- AUD-009 (публичные адаптеры Web/MCP) и AUD-012 (новый независимый holdout) этим изменением
  не закрываются. AUD-013 покрывает исправленные здесь и ранее критические контракты,
  но не означает исчерпывающего тестирования всех входных точек проекта.

Предыдущие исправления: [граница безопасного исполнения SQL](../src/adv_text2sql/sql_safety.py) и
[AUD-007/008](27_evaluation_and_label_audit.md).
