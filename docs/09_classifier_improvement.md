# Улучшение классификатора — train/dev, 29.10.2026

**Проверена первая гипотеза: обучать совместный выбор проверенных масок по качеству
ответов, вместо 16 независимых меток прироста. Преимущество на dev не получено.**
Новых LLM-запросов и оценивания новой версии на test не было. Исходный
[multilabel-классификатор](08_multilabel_classifier.md) и его результаты сохранены.

## Диагностика первой модели

У исходного классификатора 16 выходов. Benefit=1 означает улучшение относительно
all-false baseline; если ответ с фичей и без неё верен, метка равна 0. Это корректно
как «наблюдаемое улучшение», но такая цель не равна максимальному качеству
совместной маски. При редких положительных метках безопасные фичи легко исчезают.

| Наблюдение на train/dev | Значение |
| --- | --- |
| Train | 267 вопросов, 117 положительных меток на 4 271 доступную; у некоторых фичей лишь 1–3 положительных примера |
| FEAT_14 | 10 положительных train-меток; исходная модель выбрала фичу только на 2/267 train и 0/101 dev |
| Train Ambrosia: 35 | 94/136 правильных классификаций |
| Train Ambrosia: 14+35 | 92/136 |
| Train Ambrosia: 14+32+35 | 107/136 |

Последние три строки показывают, почему нельзя решать о включении фичи только
по её отдельному приросту. Для пары 14/32 полезна совместная обработка, хотя
промежуточное добавление 14 само по себе не улучшило train Ambrosia.
Это наблюдения сохранённых проходов, а не доказанный причинный эффект.

## Ограниченный эксперимент

Реализация — [experiment_structured_classifier.py](../scripts/experiment_structured_classifier.py).
Артефакты — [comparison.md](../research_results/multilabel_structured_dev_20261029/comparison.md),
`model.json`, `head.npz`, `train_cv.json`, `training_loss.json`, `report.json`,
`predictions_train_dev.json` в той же папке.

| Изменение | Что проверяем |
| --- | --- |
| Допустимы только 35, 14+35, 14+32+35 | Все три ответа уже наблюдались для каждого вопроса; можно сделать честный offline replay |
| 35 фиксирован в основе | Не теряем представление схемы из-за редкой одиночной benefit-метки |
| Два линейных score | Score профилей: 0, z14, z14+z32; совместный профиль может победить при отрицательном z14 |
| Set-valued loss | Повышаем суммарную вероятность всех правильных профилей; не объявляем остальные правильные варианты отрицательными |
| Все три профиля правильны / все три неверны | Нет выдуманной предпочтительной маски по качеству |
| Явный complexity prior 0,01 | Слабое предпочтение меньшему числу добавок при равенстве; не измеренная стоимость токенов |

Это **структурированный классификатор трёх масок**, а не независимый multilabel
всех 16 фичей. Он нужен как ограниченный проверяемый эксперимент. Runtime первой
модели не заменён; новый формат не подключён к платному launcher.

## Выбор только внутри train

Энкодер MiniLM остаётся замороженным. Проверены четыре заранее заданных варианта:
текст + шесть признаков схемы или только текст, для каждого AdamW weight_decay
0,01 и 0,1. Во всех вариантах seed=42, lr=0,01, 120 эпох, одна и та же функция потерь.

Гиперпараметры выбраны по четырём исходным DB/family-fold внутри train. Scaler
обучается отдельно на тренировочной части каждого fold. OOF включает каждый
train-вопрос ровно один раз; внешние dev/test в folds не входят. Критерий —
средняя Accuracy двух задач по OOF, затем меньше добавочных фичей и порядок каталога.

| Вариант | Train OOF: средняя Accuracy |
| --- | ---: |
| Текст + схема, L2=0,01 | 65,38% |
| Текст + схема, L2=0,1 | 65,38% |
| Только текст, L2=0,01 | 66,48% |
| Только текст, L2=0,1 | **66,48%**, выбран по меньшему числу добавок при равенстве |
| Постоянный 14+32+35 на тех же train ID | **67,58%** |

Статический контроль лучше даже на OOF. Разница вариантов не доказывает, что
схема всегда вредна: БД и размеченных различий мало, разброс между folds велик.
После CV выбранная модель обучена на всём train; dev используется для отчёта
переноса, не для выбора кандидата.

## Результаты replay

| Часть | Подход | BIRD | Ambrosia | F1 Ambrosia |
| --- | --- | ---: | ---: | ---: |
| Train | 35 | 71/131 = 54,20% | 94/136 = 69,12% | 8,70% |
| Train | 14+32+35 | 74/131 = 56,49% | 107/136 = 78,68% | 55,38% |
| Train | Новый классификатор | **81/131 = 61,83%** | **114/136 = 83,82%** | 64,52% |
| Dev | 35 | **24/55 = 43,64%** | 34/46 = 73,91% | 14,29% |
| Dev | 14+32+35 | 21/55 = 38,18% | **36/46 = 78,26%** | **58,33%** |
| Dev | Новый классификатор | 21/55 = 38,18% | 34/46 = 73,91% | 45,45% |

Рост на train не переносится на другие БД. На dev классификатор выбирает 35 для
38 вопросов и 14+32+35 для 63; профиль 14+35 не выбирается. Снижение качества
нельзя исправлять объявлением удачным train-результата.

Это оценка по сохранённым ответам трёх конфигураций, а не повторное исполнение SQL
или новые вызовы DeepSeek. Произвольные комбинации фичей таким способом не оценены.
Предсказаний новой версии на test нет. Старый test уже просматривался на прошлых
этапах и не является новым независимым подтверждением.

## Приоритеты следующей версии

1. **Сохранить качество как основную цель.** Исследовать консервативный режим:
   статический 14+32+35 — исходное решение, отключение группы только при
   подтверждённой пользе. Пустая маска не должна быть универсальным выходом при
   неопределённости. Эту гипотезу ещё не проверяли; профили/пороги выбирать на train/CV/dev.
2. **Усилить данные.** Нужны дополнительные train-вопросы и особенно БД;
   для ключевых конфигураций — повторные проходы, чтобы оценить стабильность
   полезности. Нынешний классификатор учится на небольшом числе отличий и шуме
   одного прохода. Новые платные запросы этим экспериментом не запускались.
3. **Учить контекст полезности.** Различать эффект 32 на all-false фоне и поверх
   14+35; поддерживать группы/допустимые маски. Улучшения отдельных флагов не складываются.
4. **Проверять информативность признаков.** Из вопроса можно добавить дешёвые
   признаки агрегаций, сравнений и неоднозначности; семантика схемы может оказаться
   полезнее шести общих счётчиков. Эти варианты проверять отдельно, с групповой
   валидацией, без DB ID как модельного признака.

Увеличение энкодера, числа эпох или обучение LoRA не выбраны первым шагом:
пока не подтверждено, что проблема в ёмкости модели. Приоритет — постановка,
устойчивость данных и перенос между БД. Работа над генератором/LoRA Ильи остаётся
отдельной; его результаты могут дать дополнительные совместимые наблюдения.
