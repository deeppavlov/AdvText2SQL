Launcher `run_prompt_comparison_resume.ps1` использует внешний
`scripts/prompt_comparison_supervisor.py`. Сначала выполняется офлайн-проверка
`scripts/prepare_prompt_resume.py`, затем прежний frozen durable launcher.
Если `pending` пусты — счётчики не меняются. Если сохранён один
подтверждённый transient HTTP-сбой текущего search-job (429/500/502/503/504),
его резерв консервативно учитывается с журналом до запуска. HTTP 402/ошибки
ключа, неизвестный исход, другая фаза/job или несовпавшие резервы блокируют
продолжение. Биллинговые ошибки нельзя исправить таким учётом.
По умолчанию повтор платного запуска отключён (`--transient-resumes 0`). Явный
флаг `--transient-resumes 2` разрешает до **двух внешних продолжений** после
подтверждённых transient task-сбоев, с паузами **60 и 120 секунд**. Это максимум
три запуска дочерней кампании за одну ручную команду, не бесконечный retry.
Сам генератор по-прежнему останавливается на первом транспортном сбое; его
SDK retries, prompts и evaluator не меняются. Каждая новая оплаченная попытка
снова резервируется, неизвестный расход предыдущей консервативно учитывается,
готовые оценки читаются из checkpoint. Лимит `--max-jobs` сохраняется на всю
ручную команду и не расширяется при перезапуске.
Это явное дополнение к политике внешнего возобновления, а не скрытая замена
замороженного протокола: параметры, хеши supervisor/preparation и события
пишутся в локальный `resumption_events.jsonl`. После исчерпания двух продолжений
кампания останавливается; ошибки оплаты/ключа/БД, teacher или неизвестный исход

## Данные и неизменные условия

| Задача | Optimization fit | Inner validation | Внешний dev | Основная метрика |
| --- | ---: | ---: | ---: | --- |
| SQL / BIRD | 63 | 68 | 55 | Совпадение результатов исполнения, PostgreSQL EX |
| Неоднозначность / Ambrosia | 60 | 60 | 46 | Accuracy вердикта; дополнительно precision/recall/F1/FP |

Используются **все имеющиеся вопросы frozen train**, а не все вопросы benchmark.
Компоненты объединяют одну БД, нормализованные семейства вопросов и близкие
дубликаты по существующей `configuration_splits.py`. Разбиение балансирует
число вопросов без использования результатов моделей. Fit/inner/dev не должны
пересекаться ни по БД, ни по найденным семействам; проверка блокирует запуск.
Это эвристическая защита от похожих вопросов, а не гарантия отсутствия любой
семантической близости. Повторы используют одно разбиение: они измеряют
вариативность поиска/ответов, а не перенос на новые случайные наборы БД.

Все методы используют настоящий текущий генератор, признаки **14+32**, одинаковые
retry, SQL output guard и evaluator. Пустая замена обоих seed-slot побайтно
воспроизводит исходные шаблоны. Для taxonomy защищены вопрос, интерфейс схемы и
JSON-контракт; изменяется тело правил. Одновременно оба slot не оптимизируются.
Few-shot не включает gold текущего fit-вопроса; на inner/dev допустимы только
fit-примеры. Один пример содержит свою схему, вопрос и ответ; общий предел двух
демонстраций — 40 KB UTF-8. Фактически подставленные ID сохраняются в evaluations.

Неверный SQL — отрицательный результат модели. Потеря связи/неизвестная стоимость
API — остановка, не отрицательная метка. Перед SQL-поиском все выбранные эталоны
исполняются read-only; для Ambrosia проверяется соответствие схем.

## Интеграции и пределы сравнения

Используются реальные библиотеки, не три варианта самописного proposer.
DSPy отвечает за предложение и выбор инструкций/наборов примеров; task-ответ
всегда формирует наш прежний pipeline. DSPy LM-adapter направляет teacher-вызовы
через общий счётчик и прямой API, без автоматического SDK retry или запасного LM.
Dataset summary получает только fit. TextGrad получает фактическое качество и
диагностику fit через StringBasedFunction; численный EX не заменяется мнением teacher.

В закреплённом DSPy штатный генератор few-shot sets при `max_bootstrapped_demos=0`
пытается выбирать размер bootstrap из пустого диапазона. В отдельном адаптере
вместо него создаются наборы через официальный LabeledFewShot: пустой контроль
и случайные наборы до двух fit-примеров. Proposer и байесовский поиск MIPROv2
остаются официальными. В instruction-only демонстрации не используются даже
для скрытого bootstrap. Это **ограниченный labeled-only вариант MIPROv2**;
выводы не распространяются на bootstrap chain-of-thought и все настройки DSPy.

| Предел | Один поиск | Общая серия, включая подтверждение |
| --- | ---: | ---: |
| Различных оценок кандидат/вопрос | 800 | 20 000 |
| Task API calls | 1 800 | 45 000 |
| Teacher calls | 48 | 1 400 |
| Все токены | 6 млн | 60 млн |
| Активное время | 4 ч | 48 ч |

Это **жёсткие верхние пределы, не прогноз расхода**. Глобальный предел может
остановить серию до всех 24 поисков: автоматически повышать его нельзя.
До запуска по всей очереди измеряем первый job, затем уточняем стоимость и время.
При тарифах Flash на 05.11.2026 без cache hit верхняя оценка для 60 млн токенов
по пиковому выходному тарифу $1,20/млн — **$72**. Это намеренно грубая граница
для случая, когда все токены выходные; оценка по реальной доле входа/выхода будет ниже.
Она не является ограничителем списаний в долларах: ограничитель в коде — токены.
[Тарифы DeepSeek](https://api-docs.deepseek.com/quick_start/pricing/).

Максимум task-output — 4096 токенов; teacher-output SQL — 4096, ambiguity — 8192.
Каждый HTTP-запрос сначала резервирует консервативный объём в локальном и общем
счётчике. API usage закрывает резерв. При неизвестном исходе резерв сохраняется
и блокирует продолжение до разбора: его нельзя удалять ради обнуления расходов.

GEPA ограничен числом оценок и teacher-бюджетом. TextGrad делает до 12 шагов,
MIPRO предлагает восемь instruction candidates и выполняет 12 поисковых trials
с промежуточными полными оценками. Эти числа не равны стоимости: сравниваем
качество **и фактический расход** при общей оболочке бюджетов. При исчерпании
бюджета выбираются только полностью проверенные на inner кандидаты; неполные
результаты не достраиваются нулями. В ничьей предпочитается исходный промпт,
затем меньше демонстраций и более короткая инструкция.

## Ручной запуск

Зависимости установлены отдельно в `.cache/prompt_comparison`. Рабочая `.venv`
и старый `.cache/prompt_optimizer` не изменяются; сначала импортируются имеющиеся
пакеты рабочего окружения, отсутствующие берутся из нового target. Их версии и
исходники фиксируются в манифесте. Для установки на другой машине:

```powershell
.venv\Scripts\python.exe -m pip install --target .cache/prompt_comparison --upgrade -r requirements-prompt-comparison.txt
```

Подготовка без SSH/LLM:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File local/run_prompt_comparison.ps1 --prepare
```

**Первый запуск — один MIPROv2 instruction-only поиск SQL:**

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File local/run_prompt_comparison.ps1 --phase search --slot sql --method mipro_zero --repeat 1 --max-jobs 1
```

Сначала оценить его результаты и расход. Для продолжения всей очереди той же
серии (завершённые поиски пропускаются):

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File local/run_prompt_comparison.ps1 --phase search --max-jobs 24
```

Просмотр/пересчёт таблицы без SSH/LLM:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File local/run_prompt_comparison.ps1 --status
powershell -NoProfile -ExecutionPolicy Bypass -File local/run_prompt_comparison.ps1 --report
```

По умолчанию `--max-jobs 1`. При обычном запуске launcher сам поднимает SSH через
`local/start_tunnel.sh`, ждёт порт 5444 и закрывает свой процесс туннеля при выходе.
Те же команды продолжают прерванный поиск: ответы task и teacher кэшируются,
счётчики сохраняются. Разные методы/повторы не делят task-ответы. Источники и
зависимости после `--prepare` не менять: иначе проверка требует новую серию.

### Таймаут TextGrad 06.11.2026 и восстановление

В 12:13 МСК `sql__textgrad_zero__r1` остановился на BIRD №320:
DeepSeek не вернул ответ за внешний deadline **180 секунд**. Это API timeout,
а не SQL-ошибка или разрыв PostgreSQL. Сохранены 230 оценок и четыре teacher-ответа;
два TextGrad-шага записаны, внутренняя проверка второго шага не завершена.
Ошибка транспорта не записана как отрицательная оценка вопроса.

В обоих budget-файлах остался резерв одного task-вызова **12 279 токенов**.
`scripts/recover_prompt_timeout.py` офлайн преобразовал его в консервативно
учтённый расход. Фактическое списание провайдера неизвестно: поле
`unknown_usage_tokens` хранит этот предел отдельно, реальные `prompt_tokens`,
`completion_tokens` и число вызовов не менялись. Теперь `tokens` означает
измеренные токены **плюс консервативно учтённый неизвестный расход**. Локальный
и глобальный счётчики отражают один и тот же вызов; суммировать их нельзя.

Журнал `recoveries/timeout_569a251901c66208afbf.json` содержит исходные значения,
новые значения и SHA неизменённых результатов. Восстановление применено;
повторное применение не увеличивает расход. Неполная запись двух файлов после
ошибки IO может быть завершена по журналу, чужие изменения блокируют запись.
Четыре офлайн-теста прошли, хеши frozen runtime и сохранённых ответов совпадают.

Утилита не запускает API/SSH и не меняет runtime, лимиты, результаты или
экспериментальный манифест. Для аналогичного task timeout после проверки статуса:

```powershell
.venv\Scripts\python.exe -X utf8 scripts/recover_prompt_timeout.py --job sql__textgrad_zero__r1
.venv\Scripts\python.exe -X utf8 scripts/recover_prompt_timeout.py --job sql__textgrad_zero__r1 --apply
```

Сейчас эти команды повторять не требуется. Продолжение текущей очереди:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File local/run_prompt_comparison.ps1 --phase search --slot sql --repeat 1 --max-jobs 3
```

Завершённые MIPRO instruction-only и GEPA пропускаются, TextGrad восстанавливает
уже сохранённые оценки/teacher-ответы, затем запускается MIPRO few-shot.
Незавершённый №320 требует повторных task-вызовов; прежние вызовы и неизвестный
расход из счётчиков не удаляются. Сам платный запуск пользователь выполняет вручную.

### HTTP 503 во втором повторе TextGrad 06.11.2026

В 19:39:51 МСК `sql__textgrad_zero__r2` остановился на BIRD №260

## Подтверждение и правило вывода

После всех 24 поисков фиксируется таблица кандидатов до первого dev-вызова:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File local/run_prompt_comparison.ps1 --phase confirm
```

Для каждого slot и seed проверяются исходный промпт, фиксированный few-shot
и четыре выбранных метода на **основном benchmark этого slot**, при маске14+32.
Итого до **1818 dev-оценок**: `(55 + 46) × 6 условий × 3 повтора`.
Совпадающие кандидаты внутри повтора используют один ответ; между повторами
кэш не переносится. Teacher на этом этапе не вызывается. Никакие dev-ошибки
не возвращаются в proposer. Матрица all-false/14+32 и объединение двух лучших
slot — отдельная последующая проверка взаимодействий, здесь она не запущена.

В таблицах показываются исходное/выбранное качество, парные исправления и
ухудшения, ошибки генерации, среднее/SD по повторам, токены и число вызовов.
Для Ambrosia JSON дополнительно содержит precision/recall/F1/FP.
Одиночный лучший seed не подменяет итог по трём повторам. Один-два исправленных
вопроса на 55/46 сами по себе не дают устойчивого доказательства превосходства.
Просмотренные dev/large остаются ретроспективными: независимый итог потребует
новых заранее отложенных вопросов/БД. Автоматической замены рабочего промпта нет.
