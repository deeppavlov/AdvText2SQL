### Что объясняет расхождения

**BIRD.** При новой генерации относительно переоценённых старых ответов исправлены три вопроса
(`517, 829, 1512`), ухудшились шесть (`57, 34, 179, 199, 421, 803`). Для всех шести сохранённый SQL
совпадает с сырым ответом LLM: эти различия уже присутствуют на выходе модели. Среди примеров —
лишний фильтр, `COUNT(*)` вместо `COUNT(DISTINCT ...)`, лишняя колонка и изменение регистра литерала.
В вопросе `34` модель добавила `NUMERIC` в деление. Проверка ниже подтвердила: отказ вызван
числовой точностью, а не выбором другой школы или другой формулы.

Только **вопрос 1473** изменил оценку при пересчёте прежнего SQL: 1 → 0. Исторический преобразователь
восстановлен из Git с проверкой SHA; при той же установленной версии SQLGlot переводы **всех 241
эталонов совпали с текущими**. Поэтому потерю нельзя автоматически объяснять изменением перевода.
Последующая проверка в PostgreSQL подтвердила нестабильность последних разрядов параллельного
`AVG` и ложный отказ при точном сравнении. Подробности и контроль без параллелизма приведены ниже.

В свежем BIRD есть один ответ из нескольких SQL-операторов (`173`) и три ошибки PostgreSQL:
`169, 1529` — применение `TO_DATE` к колонке типа даты; `506` — отсутствующая колонка.
Все четыре вопроса имели score=0 и прежде, поэтому эти ошибки не объясняют уменьшение числа
правильных ответов. Возвращать небезопасные regex-переписывания ради их исправления не следует.

**Ambrosia.** Потеряны четыре решения: `32, 127, 131` стали пропущенными неоднозначностями,
`270` — ложным срабатыванием. Для каждого из них старые и новые входные `messages` совпадают,
оба ответа детектора проходят строгий JSON-контракт. Проверены все 123 ответа taxonomy в каждом
прогоне: невалидных нет. Следовательно, эти четыре потери связаны с изменившимся решением LLM
при тех же сообщениях, а не с отклонением JSON новым валидатором. Теперь TP=28, FP=9, FN=35, TN=139.

**Вывод:** технически серия полная, массовой поломки измерения не найдено. Одного повтора
недостаточно ни для доказательства устойчивой деградации, ни для заявления о сохранении качества.
Числовые случаи BIRD `1473` и `34` проверены; общий контракт реализован и проверен отдельно:
[точная EX, стабильное выполнение и диагностика точности](30_bird_numeric_contract.md).
Сопоставление переноса числовых типов с оригинальными SQLite-базами остаётся отдельной задачей.
Опорные метрики и исправления аудита остаются отдельными версиями;
промпты по ошибкам полного набора здесь не подбирались.

## Числовая проверка BIRD 1473 и 34

16.11.2026. Выполнено только чтение PostgreSQL: read-only транзакции, timeout 30 секунд,
общий snapshot REPEATABLE READ для сравнения вариантов. LLM-вызовов — **0**.
Проверены исходный эталон после текущего перевода, исторический SQL и свежий SQL;
результаты, Python/SQL-типы, планы и повторы сохранены в
`research_results/static_pipeline_audit_20261116_r2/numeric_review.json`.
Производственный код, checkpoint, бюджеты и сохранённые scores не изменялись.

| Вопрос | Эталон PostgreSQL | Свежий SQL | Причина отказа текущего evaluator |
| --- | --- | --- | --- |
| 1473 | `459.95626421124325`, `double precision` в первом чтении | `459.9562642112432`, `double precision` | Разница около **5,68 × 10⁻¹⁴** из-за порядка параллельного суммирования; требуется точное равенство |
| 34 | `0.20174165`, `real` | `0.20174165457184325109`, `numeric` | Разница около **4,57 × 10⁻⁹** из-за разной точности вычисления одного отношения |

**1473: подтверждённая нестабильность измерения.** Все варианты выбирают одно и то же мультимножество
из **178 337 строк**. Планы содержат `Gather` и частичные агрегаты; при повторении одного SQL
на одном snapshot последние разряды результата меняются. Реальный неизменённый `Session.score`
в этом контроле дал историческому SQL 1, свежему 0, хотя оба выражают тот же `AVG / 12`.
После `SET LOCAL max_parallel_workers_per_gather = 0` все три SQL в **трёх повторах** вернули
строго одинаковое значение `459.95626421124274`. Это локальная настройка диагностической
транзакции: серверные и рабочие настройки pipeline не менялись. Одно отключение параллелизма
не является общим решением проблемы числового сравнения.

**34: подтверждённая разница точности.** Найдена одна школа; точный фильтр имени эталона и
более широкий `ILIKE` модели выбрали те же данные. Числитель **139**, знаменатель **689**.
Исторический SQL и PostgreSQL-эталон считают в `REAL`, свежий ответ — в `NUMERIC`.
Различие сохраняется во всех повторах и без параллелизма. Арифметический контроль SQLite
возвращает `0.20174165457184326`, согласующийся с более точным отношением свежего ответа.
Это воспроизведение скалярного деления на наблюдаемых значениях, **не выполнение оригинальной
базы SQLite** и не доказательство полной эквивалентности переноса бенчмарка.

**Ограничение и следующий шаг.** Оба отказа нельзя трактовать как доказанные ошибки смысла SQL.
Однако вручную начислять баллы, округлять весь результат или подбирать допуск под два вопроса
нельзя. После сверки с официальным кодом сохранена строгая EX; для оценки BIRD локально отключён
параллелизм, добавлена отдельная числовая диагностика без влияния на score. Реализация, тесты и
проверка двух вопросов — в [отчёте контракта](30_bird_numeric_contract.md). Полные метрики r2
здесь остаются историческими; новые правила требуют отдельного пересчёта сохранённых SQL.

## Зафиксированный протокол

| Профиль | Вопросы | Фичи, остальные false | Промпты | Историческая опора |
| --- | ---: | --- | --- | --- |
| BIRD | 241 | 2+7+14+32+35 | Выбранный SQL MIPRO seed 43, demos=[]; исходный taxonomy | 132/241, EX 54,77% |
| Ambrosia | 211 | 14+32 | Исходные SQL/taxonomy | 171/211, Acc 81,04%; F1 60,78%; recall 49,21% |

Модель и endpoint берутся из `.env.deepseek` и должны совпадать с историческими full.
Ключ можно заменить; он не попадает в манифест. Флаги и DATASET_SIZE в env для этой
серии не выбирают конфигурацию: runner явно задаёт сохранённые профили и списки вопросов.
Используется прежний task-only runtime с реальным новым генератором и evaluator,
temperature=0, cap ответа 4096, без повторов HTTP-клиента и без teacher.
Историческое поле public_model.max_tokens=2048 было номинальным; фактический task-клиент
в исходных full-скриптах тоже задаёт 4096. Этот нюанс явно записан в новом протоколе.

## Последовательность ручных команд

Из корня проекта в PowerShell с доступным Bash (например, Git Bash) либо в Bash.
Все команды используют отслеживаемый Bash launcher, отдельный терминал для SSH не нужен.

**1. Зафиксировать новый протокол, без API/SSH/БД:**

```bash
bash local/run_static_pipeline_regression.sh --prepare
```

Текущий каталог — `research_results/static_pipeline_audit_20261116_r2/experiment.json`.
В нём закреплены вопросы и эталоны, выбранные промпты, маски, исторические ответы,
модель, версии библиотек, хеши текущих исходников и лимиты. Старые манифесты остаются
неизменными: их нельзя продолжать на новом коде с заменой SHA задним числом.

**2. Пересчитать сохранённые ответы, без вызовов LLM:**

```bash
bash local/run_static_pipeline_regression.sh --action reevaluate --benchmark both
```

BIRD выполняет gold и сохранённый SQL в PostgreSQL с read-only boundary и timeout;
Ambrosia пересчитывает строгую правильность решения о неоднозначности.
Исходный эталон проверяется как SQLite; после перевода AST результат проверяется как
PostgreSQL. Неработоспособный эталон остаётся `reference_error` с `score=null`, знаменатель не уменьшается.
Серия проверяет оставшиеся эталоны и сохраняет диагностику. Инфраструктурный обрыв
останавливает выполнение без модельной метки. Подтверждённые ошибки соединения при чтении
эталона повторяются максимум три раза с задержками 5/10 секунд и новой read-only транзакцией.
Ошибки SQL и statement timeout не повторяются автоматически. В progress/events сохраняются
ID вопроса/БД, тип исключения, SQLSTATE и номер попытки без текста исключения/реквизитов.
При неполной/заблокированной переоценке
свежая генерация соответствующего бенчмарка запрещена до LLM-вызовов.

**3. Свежий BIRD, один профиль, 241 вопрос:**

```bash
bash local/run_static_pipeline_regression.sh --action run --benchmark bird
```

**4. Свежая Ambrosia, один профиль, 211 вопросов:**

```bash
bash local/run_static_pipeline_regression.sh --action run --benchmark ambrosia
```

Альтернатива шагам 3–4: последовательный запуск обоих профилей одной командой,
после успешной переоценки обоих:

```bash
bash local/run_static_pipeline_regression.sh --action run --benchmark both
```

Сохранённые завершённые ответы повторно не генерируются. После остановки можно повторить
ту же команду при неизменном протоколе. Неучтённая API-reservation блокирует продолжение;
при ней нужно разобрать сохранённые budget/transport-события, а не обнулять счётчики.
Во время серии не изменять зафиксированные исходники, пакеты, модель и исторические файлы.

**5. Посмотреть состояние и итоговое сравнение, без соединений:**

```bash
bash local/run_static_pipeline_regression.sh --status
bash local/run_static_pipeline_regression.sh --report
```

Просмотр плана без записи результатов/соединений:

```bash
bash local/run_static_pipeline_regression.sh --dry-run
```

## Восстановление первого пересчёта

Первая версия остановилась перед вопросом BIRD 1385: журнал SSH содержит timeout banner
exchange, при диагностике порт 5444 не ответил. SQL этого вопроса проходит локальные проверки;
точное исходное исключение в первой версии не сохранялось, поэтому причина того конкретного
DB-отказа не доказана. Исходные файлы первого запуска оставлены в
`research_results/static_pipeline_audit_20261116/`.

Отдельно исправлена ошибка preflight: 15 исходных SQLite-запросов с backtick-именами ранее
ошибочно проверялись как PostgreSQL и получили `UnsafeSQL` до перевода. Теперь все 241
эталон проходят локальную AST/safety-проверку; это ещё не подтверждение исполнения в БД.

В r2 офлайн перенесены **173 завершённых оценки**. Все прежние 15 `reference_error`
будут проверены заново, вместе с 53 ещё не обработанными вопросами. Осталось **68 BIRD-вопросов**
на момент восстановления. Текущий gold, вопросы, модель, промпты и фичи не менялись.

Перенос записан в `checkpoint_transfer.json`, копии прежних JSON — в `recovery_source/`.
Проверены SHA всех 57 файлов предыдущего runtime из локального архива; изменения разрешены
только в четырёх файлах исправления. AST тела преобразователя совпадает после отделения
новой проверки входного SQLite, а PostgreSQL execution boundary, scorer, построение
task-клиента и класс AuditSession не менялись. Зависимости и данные совпали. Таким образом,
перенесённые успешные оценки не выдаются за новые DB-измерения. Платные ответы и ledgers
не переносятся. Исторические SHA не переписаны.

Восстановление уже выполнено без соединений. Продолжать обычной командой шага 2;
по умолчанию launcher теперь использует r2. После этой правки прошли **130 тестов и 70 subtests**,
включая SQLite-идентификаторы, запрет вредоносного SQL, ограниченные retries, диагностику
и сохранение прежних файлов при переносе. Ruff прошёл.
