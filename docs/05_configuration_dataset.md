# Phase 0.2 — датасет полезности конфигураций

**Статус: выполнено 28.10.2026.** Собраны 468 записей, проверены источники,
построены групповые train/dev/test и CV. Обучения и новых LLM-запросов не было.

Данные — [`data/configuration_utility/deepseek_20261028/`](../data/configuration_utility/deepseek_20261028/summary.md).
Воспроизводимый builder — [`scripts/build_configuration_dataset.py`](../scripts/build_configuration_dataset.py).
Исторические `feature_labels*.json` и старый `build_feature_dataset.py` не изменялись
и не использовались как источник новой разметки.

## Источники и кандидаты

Использованы завершённые DeepSeek-прогоны из [одиночной серии](03_deepseek_ablation.md)
и [проверки комбинаций](04_deepseek_combinations.md). Модель, настройки API,
генератор, промпты, evaluator и датасеты проверяются на совместимость по metadata
и сохранённым протоколам. Замороженные контролы проверены по хешам.

| Имя в датасете | Флаги | Назначение |
| --- | --- | --- |

| `economical` | 35 | Кандидат первого селектора |
| `hybrid` | 14,32,35 | Основная статическая опора и кандидат селектора |
| `relationships` | 1,14,32,35 | Дополнительное наблюдение; не основная цель выбора |

| Данные | BIRD | Ambrosia |
| --- | ---: | ---: |
| Вопросов | 241 | 227 |
| Баз | 8 | 52 |
| Правилен только hybrid | 16 | 33 |
| Правилен только economical | 13 | 13 |

Итого только **75 из 468** строк дают наблюдаемое различие качества основных
кандидатов. Оракул не является результатом обученного селектора. Small-наборы
не добавлялись: все 22 BIRD small и 24 Ambrosia small уже входят в эти данные.
Результаты GPT/Mistral не смешаны с DeepSeek.

В cost-aware targets hybrid выбран лишь в 49/468 строках. Предсказание «всегда
economical» даст 89,53% совпадений с этими targets, поэтому accuracy самого
классификатора не является критерием успеха: оцениваем downstream качество и расход.

## Разметка

| Поле | Значение |
| --- | --- |
| `outcomes.<config>.correct` | Правильность сохранённого ответа, отдельно от полезности |
| `observed` | Наблюдение доступно; отсутствие сохраняется как false с correct=null |
| `utility_vs_baseline` | correct(config) − correct(baseline), то есть −1/0/+1 |
| `utility_vs_economical` | Та же разность относительно экономичного контроля |
| `labels.quality_preference` | economical или hybrid только при различии правильности; при ничьей null |
| `quality_preference_observed` | Маска строк с различием качества |
| `labels.cost_aware_preference` | При преимуществе качества — победитель; при ничьей — economical по заранее фиксированной политике |
| `outcome_class` | hybrid_only_correct / economical_only_correct / both_correct / neither_correct |

Это **наблюдаемая полезность конфигураций в одном проходе**, а не доказанный
причинный эффект отдельной фичи. Векторы «оптимальных 33 переключателей» не
создавались; `independent_multilabel_targets_available=false`. Для независимого
выбора групп фич в Phase 2 потребуются соответствующие наблюдения и ограничения.

BIRD использует сохранённые per-question EX-подобные score локального PostgreSQL
evaluator. Ошибки выполнения SQL считаются неуспехом модели только когда в error
однозначно указан её SQL; ошибка эталона или нераспознанный сбой не превращаются
в отрицательную метку — сборка останавливается. В текущих источниках все ошибки
исполнения относятся к предсказанным SQL. Перезапуска SQL при сборке не было.

Ambrosia использует `ambrosia-strict-v1`: `error` всегда неверен. Метрика означает
детекцию неоднозначности, а не проверку SQL. Задачи и исходные labels хранятся
раздельно по benchmark/task.

## Входы и стоимость

В `inputs` доступны только **question, evidence и schema_stats**. Последние —
число таблиц/колонок и колонок текстовых, числовых, временных, булевых типов.
Они восстановлены из сохранённых TSV-схем economical для всех 60 БД. Использованы
только однозначные соответствия вопроса и БД; противоречивые схемы отклоняются.
Табличные данные, эталонный SQL и ответы модели для построения этих признаков не нужны.

`db_id`, benchmark, difficulty, gold_ambiguous, семейства, split и правильность
находятся вне модельных входов. `inputs.jsonl` экспортирует только ID и объект inputs;
ID служит ключом сопоставления и не должен попадать в текст классификатора.

В raw responses нет надёжного question_id для точного учёта затрат. Поэтому
персональные prompt_tokens/completion_tokens оставлены **null**, а
`question_cost_observed=false`. В manifest сохранены измеренные итоги прогонов,
число вызовов и среднее, включающее probe/build. Среднее не выдано за измерение
конкретного вопроса. Выбор economical при ничьей — политика на уровне конфигурации.

## Разделение

Одинаковые БД, нормализованные вопросы и семейства объединяются в связные компоненты.
Для Ambrosia учитывается `ambig_question`, связывающий неоднозначную формулировку
с её вариантами. Нормализация учитывает Unicode, регистр, пунктуацию, числа и
цитируемые значения. Между БД дополнительно связываются консервативно близкие
вопросы: минимум 8 уникальных токенов, Jaccard ≥0,8 и SequenceMatcher ≥0,9.

Получено 60 компонентов; на этих данных дополнительных межбазовых near-duplicate
связей не найдено. Это проверка известных и эвристических семейств, не гарантия
семантической независимости всех возможных перефразировок.

Seed — **42**, целевые доли — **60/20/20**. Распределение балансируется только
по числу строк каждого benchmark, без использования правильности или utility.
Неделимость БД даёт отличающиеся фактические доли, особенно на восьми БД BIRD.

| Часть | BIRD, вопросов / БД | Ambrosia, вопросов / БД | Всего | Строк с различием качества |
| --- | ---: | ---: | ---: | ---: |
| Train | 131 / 4 | 136 / 23 | **267** | 42 |
| Dev | 55 / 2 | 46 / 15 | **101** | 21 |
| Test | 55 / 2 | 45 / 14 | **100** | 12 |

Пересечения ID, БД и известных семейств между частями — **0**.
Четыре CV-fold построены только внутри train; внешние dev/test в них не участвуют.
Отдельно сохранены диагностические Ambrosia holdout-fold по конструкциям
attachment (77 строк), scope (78) и vague (72). Они используют всю Ambrosia как
отдельный анализ и не должны подменять основной train/dev/test протокол.

**Test ретроспективный.** Все эти вопросы уже использовались при подборе статических
конфигураций. Кроме того, 13 вопросов Ambrosia и 18 записей по семействам имеют
нормализованные совпадения с примерами используемых статических шаблонов промптов.
Эти флаги находятся только в analysis; они отмечают возможную экспозицию, а не
доказывают конкретный вызов с таким примером. На BIRD таких совпадений нет.
Независимый финальный test ещё отсутствует: для публикационных выводов нужны
новые вопросы/БД и контроль пересечения с промптами.

```powershell
.venv\Scripts\python.exe scripts/build_configuration_dataset.py
.venv\Scripts\python.exe scripts/build_configuration_dataset.py --verify-only
```

Сборка не читает `.env`, не подключается к БД и не вызывает LLM. Исходные прогоны
не переписываются. Manifest связывает каждый источник и выходной файл с SHA-256;
verify проверяет хеши, покрытие, labels, разделение и CV.

Проверки: **55 офлайн-тестов**, Ruff, сборка реальных источников и отдельная
проверка bundle. Следующий этап — **Phase 1: rule-based selector** на зафиксированных
кандидатах. Обучение multilabel-классификатора и его интеграция ещё не выполнены.
