из проверенного датасета, подготовлены гипотезы новых комбинаций. **Новых платных

**14+32+35 — опорный компактный набор с лучшей наблюдаемой Accuracy среди проверенных

одинаковый набор для всех вопросов, а не статистическую доказанность превосходства.

## Как интерпретировать текущую реализацию

Источник истины — [генератор](../src/adv_text2sql/mcp_servers/text2sql_tool/src/text2sql_implementation.py)
и [промпты](../src/adv_text2sql/mcp_servers/text2sql_tool/src/prompts.py).
[practices_doc.md](../practices_doc.md) описывает замысел; некоторые статусы и формулировки
устарели. Ниже указана фактическая семантика, без изменения исторического кода.

| FEAT | Что реально делает | Условие, взаимодействие и смысл для поиска |
| --- | --- | --- |
| 1 | Извлекает PK/FK и добавляет их в системный SQL-промпт и классический checker | Совместима с TSV и MinHash. В taxonomy-промпт 32 связи не передаются. Добавление к H уже проверено: та же Accuracy, другие ошибки |
| 2 | Собирает статистики колонок, добавляет их в SQL-контекст и классический checker | Родитель для 3/4/7. Taxonomy 32 эти статистики не получает. Отрицательный результат 2+35 не исключает 2+3+7+35 |
| 3 | Определяет типы по значениям, включая regex для TEXT, distinct/non-null counts | Только внутри 2. При false все колонки в этой ветке получают categorical-заглушки; это больше, чем косметическая детекция TEXT |
| 4 | Получает row count через pg_stat, при отсутствии оценки — COUNT(*) | Только внутри 2. При false row_count=0, а не переключение на один лишь COUNT(*). Может менять вывод компактного форматтера 7 |
| 5 | Объявлен как light schema | Флаг не читается в выборе схемы: light используется и при false, если нет 35/6. Не отдельная ось поиска |
| 6 | DDL, sample rows и значения низкокардинальных колонок | Альтернатива light/TSV. При 35=true эта ветка не выполняется. BIRD-результат 118/241 получен с неполной подготовкой схемы; сначала исправление транзакций в новой версии протокола |
| 7 | Компактно форматирует статистики, сокращает ID и список значений | Только при 2. Для корректного определения ID нужны осмысленные distinct и row_count от 3/4; работает и без них, но иначе |
| 8 | Делает rollback в отдельных обработчиках ошибок статистик | Поддержка надёжности ветки 2. В heavy-цикле 6 этих guards нет: включение 8 само по себе его дефект не исправляет |
| 9 | Разрешает dump db_schemas.json в BaseBenchmark.build | Текущий исследовательский runner строит инструменты другим путём; здесь dump не вызывается. Не ось качества |
| 10 | Логирует длительность build и размер контекста | Наблюдаемость, не SQL-техника |
| 11 | Добавляет файловый JSON-handler при настройке логирования | Наблюдаемость. Исторические комментарии в prompts ошибочно называют retry-шаблон FEAT_11; реальный переключатель там 27 |
| 12 | После classic ambiguous всё же пробует SQL | Не отключает checker. Для нормально сработавшего taxonomy 32 ранний return остаётся: 12 его не отменяет. При генерационной ошибке первоначальный ambiguous может сохраниться |
| 13 | Меняет простой classic checker на подробный с правилами/примерами | При 32 нормальная ветка classic не вызывается. Возможен внешний аварийный fallback; не считать безусловно эквивалентными все аварийные пути |
| 14 | Выбирает строгий SQL-шаблон вместо basic | Дополнительные правила, не отдельный генератор. При 29 действует на moderate-ветке, simple/complex выбирают другие шаблоны; при feedback 27 шаблон снова другой |
| 15 | Санитизирует markdown, некорректный DISTINCT и отдельные CAST/NULLIF | Совместима с 16/17/27/28. Часть очистки и SQL-исправлений выполняется всегда, поэтому all-false уже содержит постобработку |
| 16 | Проверяет полноту SELECT/FROM, парсит SQLGlot, отклоняет Drop/Delete/Update | Это не PostgreSQL EXPLAIN и не полная гарантия read-only. Без 17 не исправляет отклонённый SQL; с 17 создаёт сигнал для повтора |
| 17 | Повторяет генерацию при её ошибке или отказе judge 20 | В протоколе MAX_RETRIES=5, при false одна попытка. Это алгоритмическая стратегия и часть поиска, а не просто инфраструктура; при 28 цикл обходится |
| 18 | Меняет число/задержки транспортных повторов rate-limit | Поддержка доступности API. Не смешивать с SQL-повторами 17. При false транспортные повторы всё равно частично есть |
| 19 | Добавляет паузу между вопросами в benchmark.predict | Расписание запросов, не семантика SQL |
| 20 | Просит LLM проверить соответствие SQL вопросу, принимает только OK | Без 17 это reject-only, с 17 — перегенерация, с 27 — ещё и текст причины. Judge не получает схему/результат выполнения. При 28 не вызывается |
| 21 | Ищет похожие множества значений TEXT/VARCHAR и добавляет до 10 возможных связей | Независима от 1: сходство значений не является FK. Только SQL-system prompt. Python hash и выборка LIMIT без ORDER BY требуют контроля воспроизводимости |
| 22 | Retrieval значений через LSH/vector DB | Не реализована, переменной FEAT_22 нет |
| 23 | Генерирует описания таблиц по их именам/колонкам, кэширует по db_id | Только SQL-system prompt, не расширяет taxonomy 32. До одного LLM-вызова на таблицу при холодном кэше; кэш фиксировать вместе с моделью/схемой |
| 24 | Извлекает скрытые связи из внешнего query-log | Не реализована |
| 25 | Просит LLM выбрать релевантную схему и добавляет ответ в user message | Полная схема остаётся в system prompt; это дополнительная подсказка, а не настоящее сокращение контекста. При retries/voting вызов повторяется на каждую генерацию |
| 26 | Читает до 10 прежних Q/SQL при build, сохраняет новые «успешные» SQL | Success здесь не означает правильность или успешное выполнение. Холодный изолированный прогон не проверяет ценность накопленной памяти; текущий system prompt не перечитывает файл после каждого вопроса |
| 27 | Передаёт прежний SQL и ошибку в специальный retry-промпт | Нужен 17 и реально отклонённая попытка. Полезная группа: 16+17+27, затем 20. Ошибки PostgreSQL из benchmark.evaluate назад в query не поступают |
| 28 | Генерирует три SQL и голосует по нормализованным строкам | Отдельная стратегия вместо цикла 17/20/27. Это не голосование по результатам исполнения; при равенстве выигрывает первый. lower() применяется и к литералам, поэтому возможны ложные совпадения строк |
| 29 | Эвристически выбирает simple/moderate/complex SQL-шаблон | Не полный конфликт с 14: moderate использует 14. Дополнительно управляет тем, на каких вопросах вызывается 30; нельзя автоматически запрещать пару 14+29 |
| 30 | Отдельным LLM-вызовом строит план и подмешивает его перед SQL | Без 29 complexity=None, значит вызов для всех дошедших до генерации вопросов. С 29 — moderate/complex. С 28 план вычисляется, но не передаётся в voting.generate_sql: текущая комбинация тратит вызов впустую |
| 31 | Отдельного переключателя в текущем генераторе нет | Не ось реализованного пространства конфигураций |
| 32 | Stop-filter и LLM-проверка паттернов AND-scope, every/each и расплывчатого термина A1 | Фактически не полное покрытие A1–A6. Получает question и db_schema, не PK/FK/stats/descriptions. Обычно заменяет classic checker. Внутренние ошибки ловятся и возвращают non-ambiguous |
| 33 | При detected ambiguous генерирует уточнение | Требует 32. Без 34 итог всё равно status=ambiguous; вопрос/варианты наружу не возвращаются. Для текущего batch-скоринга это дополнительные расходы, а не новая детекция |
| 34 | LLM сама выбирает интерпретацию, переписывает вопрос и идёт к SQL | Требует 32+33. Нет ответа пользователя. Это другой режим задачи: Ambrosia ожидает ambiguous, а здесь сигнал превращается в SQL; проверять отдельно как разрешение неоднозначности |
| 35 | Выбирает TSV table/column/type | Альтернатива light/heavy, но совместима со статистиками и связями. Имеет приоритет над 6. Меняет схему и в SQL, и в детекторе |
| 36 | Внутри sanitizer добавляет LIMIT 101 при отсутствии LIMIT/FETCH | Требует 15. Может обрезать правильный ответ BIRD; годится для интерактивной пагинации, не эквивалентна оптимизации полного EX. Поиск LIMIT по всему SQL также видит вложенные LIMIT |

## Зависимость, перекрытие и непригодность для метрики — разные вещи

| Тип отношения | Примеры | Как учитывать |
| --- | --- | --- |
| Жёсткое условие активации | 3/4/7 → 2; 33 → 32; 34 → 32+33; 36 → 15 | Проверять дочернюю фичу поверх включённого родителя, не повторять её одиночный no-op |
| Условие полезного повторного действия | 27 → 17 и предыдущая ошибка; 20 без 17 может только отбраковать | Изучать цепочками с промежуточными контролями |
| Приоритет альтернатив | 35 перекрывает 6; 28 обходит 17/20/27 | Хранить один канонический профиль вместо нескольких одинаковых по рабочей ветке масок |
| Частичное перекрытие | 29 меняет 14 только для simple/complex | Сочетание допустимо; сравнивать профили, не объявлять жёстким конфликтом |
| Потеря аргумента / реализации | 30+28 не передаёт план; 25 не убирает полную схему | Не приписывать результат задумке, которая в коде не выполняется; исправленная версия — отдельный эксперимент |
| Смена задачи | 34 auto-resolve; 36 pagination | Отдельная метрика и протокол, а не автоматическое утверждение «плохая фича» |
| Инфраструктура / no-op | 8/9/10/11/18/19, неэффективный 5 | Не предсказывать как per-question SQL-полезность. Фон фиксировать и описывать |

Ранее в multilabel-декодере пары **14/29, 20/28, 12/32** исключались как консервативное
ограничение модели. Это не три равнозначных доказанных конфликта генератора.
Особенно запрет 14+29 искусственно сужает поиск. Замороженную v1 не переписываем;
следующая версия должна использовать описанные выше типы отношений.

Пространство действительно сокращается. Например, у блока {2,3,4,7} 16 бинарных
масок, но только **9 различных профилей по действующей ветке**: statistics off и
8 настроек при включённой 2. У {5,6,35} восемь масок сводятся к трём представлениям.
Тем не менее, после зависимостей остаются независимые способы передачи знания,
SQL-промпты и стратегии генерации. По этим примерам нельзя вычислить размер всего
пространства: отношения пересекаются, аварийные пути и состояние кэшей тоже различаются.

## Почему одиночные результаты ценны

| Фича | Изменение BIRD к baseline | Исправлено / испорчено | Что проверять дальше |
| --- | ---: | ---: | --- |
| 2 | +10 ответов | 18 / 8 | Статистики в контексте H; варианты 3/4/7 |
| 14 | +9 | 16 / 7 | Удаление из H и совместная работа с 29 |
| 25 | +8 | 13 / 5 | Дополнительная релевантная схема поверх H; отдельно настоящий pruning после исправления |
| 29 | +7 | 12 / 5 | Routed-промпты поверх H, затем совместно с 30 |
| 23 | +2 | 11 / 9 | У отдельных вопросов есть выигрыш, несмотря на слабый средний эффект |
| 30 | 0 | 13 / 13 | Нейтральное среднее скрывает разные ответы; проверить в подходящем контексте |

У 3/4/7 одиночный прогон по существу не активировал механизм; это полезное
обнаруженное ограничение протокола, а не провал самой техники. Прогон 6 выявил
проблему подготовки схемы; прогон 20 — цену reject-only и ошибку legacy-метрики.
Без одиночной серии этих сведений не было бы.

Один проход при temperature=0 всё равно не гарантирует идентичные ответы API.
Повторы ключевых контролей нужны для оценки устойчивости, особенно когда разница
один-два вопроса. Результаты неактивных флагов дают предупреждение о вариативности,
но не являются полностью контролируемыми повторностями одной конфигурации.

## Что означает «лучший» для двух бенчмарков

**BIRD здесь измеряет исполнение SQL и совпадение результата; Ambrosia — классификацию
ambiguous / not ambiguous. SQL-корректность на однозначных Ambrosia текущий оценщик
не проверяет.** При strict-политике error и пустой ответ всё равно считаются неверными.

При неизменной схеме и 32 вход taxonomy одинаков для H, H+1, H+14, H+21, H+23 и многих
других SQL-комбинаций. Это ограничение покрытия детектора, а не конфликт этих фичей.
Их влияние на Ambrosia возможно через ошибки генерации, аварийные пути и вариативность
новых ответов детектора, но нельзя обещать ими прямое улучшение детекции.

Нужны два отдельных лидера и общий компромисс. Для общего набора заранее фиксируем
основной скор: **среднее Accuracy BIRD и strict Accuracy Ambrosia с равным весом**;
параллельно показываем оба результата, F1/recall/FP Ambrosia, ошибки, входные/выходные
токены и число LLM-вызовов. Если одна конфигурация лучше на BIRD, другая на Ambrosia,
не скрываем это одним числом: сохраняем обе на границе качества/расхода.

## Последовательность поиска

H обозначает 14+32+35. Ниже — **меню гипотез**, а не инструкция немедленно выполнить
все прогоны. Полные явные маски и контрольные пары экспортирует
[audit_static_hybrid.py](../scripts/audit_static_hybrid.py).

| Шаг | Кандидаты | Зачем и сколько новых масок |
| --- | --- | --- |
| 1. Замкнуть ядро | 14+32; 32+35 | Не хватает двух из восьми подмножеств {14,32,35}. Проверить необходимость каждого компонента, включая взаимодействия; 2 маски |
| 2. Добавления к H | +2, +15, +16, +21, +23, +25, +28, +29, +30 | Проверить девять действующих механизмов в сильном контексте. H+1 уже измерен; 9 масок |
| 3. Зависимая группа статистик | H+2+7 → +3 → +4 | Не выбирать статистики только по одиночному 2. Сравнение с H+2 и соседними шагами; 3 маски |
| 4. Группа исправления | H+15+16 → +17 → +27 → +20 | Разделить очистку, валидацию, повтор, feedback, judge. Ошибки PostgreSQL пока не поступают в feedback; 4 маски |
| 5. Осмысленные взаимодействия | H+15+16+28; H+29+30 | Проверить валидируемое голосование и декомпозицию с маршрутизацией; 2 маски |
| 6. Поиск за пределами H | Добавления, удаления и замены вокруг нескольких лидеров; согласованные пары дополнений | Не закреплять три исходные фичи навсегда и не останавливаться на одном greedy-пути; состав определяется результатами предыдущих шагов |

В меню 20 новых масок. Все на полном объёме означали бы 40 benchmark-запусков и
9 360 обработок вопросов до повторов; это **не оценка числа LLM-вызовов**. Отбор
проводить ступенчато на train, финалистов — на dev, а не сразу запускать всё целиком.
Группы 3–5 нужны и при слабом одиночном эффекте, поскольку включают отдельные
механизмы взаимодействия. Heavy 6 и stateful 26 остаются отдельными ветками после
исправления/фиксации протокола; 12/13 изучаются в classic-профилях из шага 6.

На шаге 6 сохраняем небольшую beam-группу: лидер BIRD, лидер Ambrosia и лидер общего
скора, удаляя дубликаты. Для каждого рассматриваем допустимые добавления/удаления,
замену TSV/light/heavy, classic/taxonomy и SQL/retry/vote-профилей. Сохраняем несколько
путей и проверяем семантически мотивированные пары, даже если одиночное добавление
не выиграло. Например, 1+21 — явные и предполагаемые связи, 21+23 — структурные и
семантические подсказки. Конкретные маски следующего раунда записываются до запуска.

Число фичей X **не фиксируем равным трём**. Для каждого числа включённых алгоритмических
флагов показываем лучший проверенный результат; отдельно считаем группы механизмов:
добавление 16+17+27 — три флага, но один конвейер исправления. Набор из восьми флагов
может стоить дешевле набора из четырёх, поэтому число фичей не заменяет бюджет токенов.

Все маски — с явно выключенными остальными флагами. Инфраструктуру 8/18 можно
исследовать/фиксировать отдельно, но изменение общего фона требует нового
контрольного H и нового протокола, а не смешивания старых чисел с новыми.

## Что можно доказать и когда остановиться

| Утверждение | Необходимое основание |
| --- | --- |
| «Лучший среди измеренных» | Полный реестр проверенных конфигураций, одинаковые ID и оценщик |
| «Лучший среди восьми масок ядра» | Измерить недостающие две маски; повторить финалистов для устойчивости |
| «Локальный максимум относительно выбранных групп» | Проверить заявленные добавления/удаления/замены и явно перечислить соседство |
| «Максимум во всём допустимом пространстве» | Полный перебор канонических конфигураций при фиксированном протоколе либо обоснованная верхняя граница для всех непроверенных; таких границ сейчас нет |

Поиск останавливается при заранее заданном бюджете или отсутствии улучшения в
объявленном соседстве с учётом повторов. Это не превращает локальный результат в
глобальное доказательство. Наличие зависимостей уменьшает перебор, но не делает
качество LLM монотонным или сумму одиночных эффектов достоверной.

Исторические полные наборы и прежний test уже просматривались. Их можно продолжать
использовать как исследовательский стенд с этой оговоркой. Для выбора следующего
классификатора используем групповой train/CV/dev, а для независимого окончательного
подтверждения — новые вопросы/БД без использования их ответов при выборе масок.
Новые конфигурации на test запускаем только после фиксации выбора, не для поиска.

## Следующая версия селектора

1. Сначала расширить реестр **реально выполненных совместных конфигураций** и уточнить
   статические контроли. Сохранить question_id, DB/group, точные флаги, версии схемы,
   модели/промпта/кэша, исходный ответ, качество, активированные стадии, ошибки и usage.
2. Обучать выбор между допустимыми профилями/группами с учётом их контекста. Одиночные
   метки остаются полезным сигналом, но не объявляются оптимальной совместной маской.
3. Не сводить supervision к «эта фича единственная правильная»: несколько наборов
   могут дать правильный ответ. Не смешивать неизвестное наблюдение с неудачей.
4. Сравнить динамическую политику с новым сильным фиксированным набором на одинаковых
   группах. Рост score или сохранение качества при измеренной экономии — отдельные
   цели; ухудшение обеих метрик не принимать за успешный этап.

Офлайн-аудит воспроизводится без SSH/API:

```powershell
.venv\Scripts\python.exe scripts/audit_static_hybrid.py --out research_results/static_hybrid_audit_repeat
```

Существующие результаты, модель v1, исходный генератор и обучающие датасеты этим
аудитом не изменены. Новый скрипт только проверяет исходный bundle и экспортирует
описательные числа/предложения; он не является launcher платных экспериментов.
