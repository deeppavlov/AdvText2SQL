# Сбои DeepSeek: защита транспорта и восстановление — 03.11.2026

Подготовлена отдельная версия `fail-fast-transport-v1`. Пользователь выполнил
recovery 03.11.2026: все три запуска завершены, 9 ответов восстановлены. Платные
вызовы помощником не выполнялись. Текущая рабочая папка:

`research_results/deepseek_combinations_large_20261026/final_search_20261030_transportfix/`.

## Причина и исправление

В исходной серии HTTP 503 и `AttributeError: 'NoneType' object has no attribute
'usage'` попадали в широкие catch генератора/детектора. Остановка происходила
лишь после трёх последовательных сбоев; промежуточный успех обнулял счётчик.
Поэтому некоторые вопросы получили error, другие — success после fallback
детектора. Это не чистое измерение способности модели.

| Поведение | Предыдущий runtime | Новая версия |
| --- | --- | --- |
| Исключение SDK, HTTP 503/429/таймаут | Может превратиться в model error или fallback | Первый сбой прерывает текущий вопрос и очередь до checkpoint |
| null-response / некорректный объект usage | AttributeError может быть поглощён | Терминальная ошибка границы клиента, отдельный журнал |
| Максимальное ожидание внешнего create | Несколько SDK-попыток могли занять много минут | Общий deadline 180 секунд; SDK retries=2 сохранены |
| Повтор вопроса после сбоя API | Уже сохранённый error пропускается | Прерванный вопрос не сохраняется и доступен при ручном resume |
| Невалидный JSON/SQL от модели | Обрабатывается существующим кодом | Правила сохранены; это не основание для transport replay |
| Изменение модели/фичей/промпта | — | Не выполнялось |

Новый `ResponseBoundary` поднимает существующий `ProviderUnavailable(BaseException)`,
который не поглощается `except Exception` в генераторе/детекторе. В
`transport_events.jsonl` записываются ID вопроса, этап, тип исключения и числовой
HTTP-код; текст исключения с возможными секретами не копируется. Пустой оплаченный
ответ по-прежнему сначала сохраняется вместе с usage, затем останавливает очередь.
Автоматических повторов вопроса нет, FEAT_17 не менялся.

## Что восстановить

Выбор выполнен по факту исключения клиента в блоке лога с ID сохранённого
вопроса. Gold SQL, правильность ответа и score для выбора не использовались.
Включены и `error`, и `success` после транспортного сбоя детектора.

| Исходный запуск | Бенчмарк | ID | Причина |
| --- | --- | --- | --- |
| hybrid_control_repeat__r1 | Ambrosia | 133 | null-response/usage, ранее ошибочно интерпретировался как generation error |
| hybrid_plus_2__r3 | Ambrosia | 31 | HTTP 503 при детекции и генерации |
| hybrid_plus_2__r3 | Ambrosia | 325, 326 | null-response/HTTP 503 в детекторе, далее fallback |
| statistics_compact__r3 | BIRD | 309, 326 | HTTP 503/null-response при генерации |
| statistics_compact__r3 | BIRD | 223, 295 | HTTP 503/null-response в детекторе, далее fallback |
| statistics_compact__r3 | BIRD | 323 | HTTP 503 в детекторе перед остановкой; найден полным аудитом |

Всего **9 ID в трёх запусках**. Вопрос Ambrosia 20, у которого модель вернула
`{` вместо JSON, оставлен без переигрывания: это не доказанный транспортный сбой.
Остальные обычные model errors также не отбираются для восстановления.

## Сохранение происхождения данных

- `connectionfix/` не редактировалась: все файлы train/dev сверены по SHA-256
  после копирования, исходный manifest остался прежним.
- В `transportfix/` созданы новый protocol hash и manifest с хешами новых
  скриптов; модель, маски, cohorts, оценщики и исходники генератора не менялись.
- Перенесённые metadata помечены `imported_protocol_sha256`. Эти результаты
  получены со старой транспортной защитой, а не заново измерены новой версией.
- В `recovery_plan.json` сохранены исходные ответы, причины отбора и хеши всех
  скопированных исходных артефактов. Неверные транспортные ответы удалены только
  из рабочей копии checkpoint. Старые отчёты сохранены как
  `report.before_transport_recovery.json` и аналогичный файл predictions.
- Исторические raw responses, usage и attempts сохранены; оплаченные старые
  вызовы не исчезают из учёта при восстановлении.
- Финалисты зафиксированы по неизменному исходному screening-snapshot.
  Исправление H/r1 не приводит к повторному отбору кандидатов по новым ответам.
  После восстановления контрольные метрики и Δ пересчитаются; прежние числа
  H с транспортным error 133 остаются историческими, не итоговыми.

Из-за помеченного recovery_pending у H/r1 статус новой папки временно показывает
14/15 завершённых screening-масок. Это ожидаемо: требуется восстановить один
ответ контроля, а не заново выполнить отбор всех конфигураций.

## Ручной запуск

Подготовка и recovery уже выполнены. Первоначальные команды ниже сохранены
для воспроизводимости; актуальный следующий шаг — в разделе «Результат recovery».
Проверка без файлов, SSH, БД и API:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File local/run_transport_safe_campaign.ps1 --phase recovery --dry-run
```

Первый платный шаг — восстановление и завершение трёх затронутых запусков:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File local/run_transport_safe_campaign.ps1 --phase recovery
```

| Запуск | Сохранено корректных по транспорту ID | Осталось обработать |
| --- | ---: | ---: |
| H/r1, Ambrosia | 119/120 | 1 |
| H+2/r3, Ambrosia | 117/120 | 3 |
| Compact/r3, BIRD | 3/131 | 128: 5 восстановлений и 123 ещё не обработанных вопроса |
| **Всего этой команды** | | **132 предсказания** |

«Корректных по транспорту» не означает правильный SQL. Сохранённые ответы не
отбирались по результату оценки. Исходная ошибка модели, если она повторится
без транспортного сбоя, станет обычным итогом вопроса и не будет переигрываться.

Команда recovery не запускает всю следующую серию и не начинает Ambrosia compact.
После её завершения и разбора результатов — продолжение оставшейся части
третьего train-повтора новым launcher:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File local/run_transport_safe_campaign.ps1 --phase repeat --round 3
```

До завершения recovery обычные этапы блокируются. Если сервис снова недоступен,
команда остановится; после стабилизации повторяется та же команда, сохранённые
вопросы не регенерируются. Исходный launcher `run_resilient_hybrid_campaign.ps1`
для дальнейшей работы этой серии больше не использовать.

## Проверки

**69 офлайн-тестов прошли**, включая девять новых: остановка до checkpoint при
первой ошибке клиента, обход fallback, null/usage, deadline, сохранение usage
пустого ответа, отсутствие скрытого повтора невалидного JSON, отбор transport-only
и перенос без изменения исходников. Ruff и синтаксис PowerShell/Bash проверены.
Dry-run recovery, --status и повторная --prepare прошли без SSH/БД/API. Сверены
все исходные хеши, неизменность хороших checkpoint-ответов, model/cohort identity
и прежний набор пяти профилей. Готовность самого DeepSeek сетью не проверялась.
