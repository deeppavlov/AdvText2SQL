### Фактический лимит ответа

Проверка закреплённого `prompt_pilot_runtime.py` выявила расхождение: в старых
prompt-манифестах написано `max_tokens=2048`, но native client создавался с
**4096**. Поэтому прежнее предположение, что бюджет ответа отличал их от старых
абляций, было неверным. Новый протокол явно закрепляет фактические 4096,
температуру 0, `max_retries=0`, timeout 90. В старые манифесты исправления не
вносятся; измеренный учёт токенов не пересчитывается по объявленному лимиту.

### Совместимость архивов

Проверены пять актуальных prompt-серий и последний полный статический эксперимент.
Выбор исходного ответа определяется порядком источников **до просмотра score**:
свежие full, затем исходный поиск, затем dev-повторы. Лучший ответ среди повторов
не выбирается. Модель, runtime/package identity, закреплённый генератор/шаблоны,
вопрос/evidence/эталон, схема и evaluator сверяются; ошибки SQL остаются наблюдаемыми
неудачами, транспортные сбои не становятся отрицательными метками.

| Источник | Переиспользовано train/dev-наблюдений | Решение |
| --- | ---: | --- |
| BIRD full, выбранный MIPRO + compact | 186 | 131 train + 55 dev |
| Ambrosia full, исходный 14+32 | 166 | 120 train + 46 dev |
| Исходный prompt-поиск MIPRO, та же BIRD-инструкция на 14+32 | 68 | Дополнительные train-наблюдения |
| Compact-dev и Ambrosia-dev | 0 новых | Совместимые повторы сохранены как история, но не подменяют уже выбранный ответ |
| Последний static full | 0 автоматически | Для BIRD другой промпт; у native client иной transport retry policy (2 против 0). Ambrosia можно дополнительно проверить, автоматически эквивалентность не предполагается |
| Исторический single-flag dataset | 0 автоматически | Сохранён; подробное повторное согласование старого pipeline остаётся отдельной возможностью |

Итого **420 наблюдений** и **68 условных train-пар BIRD**. Пара сравнивает
14+32 с 2+7+14+32+35: эффект относится к группе **2+7+35**. В сохранённых ответах
8 улучшений, 2 ухудшения и 58 ничьих. Индивидуальная метка FEAT_7 из этого не
выводится. Это слабые наблюдательные метки разных запусков; инструкция выбиралась
адаптивно на этих train-вопросах, причинный или независимый выигрыш не заявляется.

### Ручной запуск

Историческая команда сбора — **all-false baseline на 120 train-вопросах Ambrosia**.
Сбор уже завершён, повторять его перед обучением не требуется.
Используется локальный `.env.deepseek`:

```bash
bash local/run_classifier_v2.sh --run --split train --benchmark ambrosia --configuration baseline --max-jobs 1
```

В текущем PowerShell команда `bash` указывает на WSL. Для проверенного Git Bash:

```powershell
& "C:\Program Files\Git\bin\bash.exe" local/run_classifier_v2.sh --run --split train --benchmark ambrosia --configuration baseline --max-jobs 1
```

Офлайн-проверка очереди, без SSH/БД/API:

```bash
bash local/run_classifier_v2.sh --dry-run --split train --max-jobs 7
```

После проверки первого запуска оставшаяся train-очередь запускается той же
оболочкой с `--run --split train --max-jobs 7`, затем dev — отдельно с
`--run --split dev --max-jobs 7`. По умолчанию разрешён только **один job**.
Завершённые jobs пропускаются, внутри незавершённых используются checkpoints.
При незакрытом API-резерве продолжение блокируется: счётчики не сбрасывать,
сначала восстановить учёт. Автоматического продолжения после ошибки нет.

Лимиты новых вызовов: **5 млн токенов / 1000 task calls / 2 часа на job**;
вся очередь — **20 млн / 6000 task calls / 20 часов**, teacher=0. Это пределы,
не прогноз расхода. Кэшированные ответы не добавляются в новый платный бюджет.

Артефакты: [`experiment.json`](../research_results/classifier_v2_20261109/experiment.json),
[`archive_audit.json`](../research_results/classifier_v2_20261109/archive_audit.json),
[`датасет v2`](../data/multilabel_utility/deepseek_20261109_v2/README.md).

от 11 до 71 колонки, в двух dev-БД — **89 и 115**. Текстовых колонок в train
максимум 41, в dev — **62 и 78**. Обе dev-БД выходят за train-диапазон по этим
счётчикам. При этом точное разложение линейной разницы оценок показывает:

| Ошибочное переключение | Вклад текста в разность logits | Вклад шести счётчиков | Bias | Сумма |
| --- | ---: | ---: | ---: | ---: |
| №4: 14+32 против compact | +1,396 | +0,240 | −0,197 | +1,440 |
| №9: 14+32 против compact | +0,772 | +0,240 | −0,197 | +0,816 |

Это аддитивное разложение линейной головы, **не причинный эффект** и не разность
вероятностей. Текстовый вклад больше структурного; оснований считать удаление
счётчиков достаточным исправлением нет. Sigmoid-оценки, например 0,899 у неверного
профиля №4, не являются гарантированной или отдельно откалиброванной уверенностью.

порядок выбора архивного наблюдения не менялись.

**Вывод и следующий ограниченный эксперимент.** Сейчас обучаемость на train есть,
а полезность выбора на новых группах не подтверждена. Нужны более содержательные
входы и проверка цели выбора, а не увеличение числа эпох или числа параметров
без диагностики. Предлагаемый следующий протокол фиксируем до его запуска:

1. Добавить постоянные рабочие профили в число полноценных контролей CV.
   Проверять улучшение отдельно по задачам: усреднение скрыло обмен одного
   ответа BIRD на один Ambrosia.
2. Сравнить оценку абсолютной правильности с **прямой оценкой полезности
   переключения относительно опоры**. Метка относится к целой конфигурации и
   её контексту; выигрыш комбинации не раздаётся отдельным флагам.
3. Добавить небольшой фиксированный набор признаков вопроса и его связи со
   схемой: даты/числа/сравнения/агрегации, совпадения слов question/evidence
   с именами колонок, одинаковые или похожие имена полей разных таблиц.
   В frozen-снимках есть таблицы, имена колонок и типы, поэтому это возможно
   офлайн; сами значения данных и их распределения там не представлены.
4. Сначала сравнить ограниченные варианты только по grouped train CV. Если
   воспроизводимого выигрыша над постоянной политикой нет, следующий приоритет —
   разнообразные новые train-БД и контрольные повторы, а не платный dev-прогон.
   Порог под два уже известных dev-вопроса не подгонять.

На этапе диагностики эти изменения модели ещё не были реализованы; следующий
раздел фиксирует их реализацию и результат отдельного опыта. Диагностика завершена,
рабочие профили и статус `adopt_as_default=false` сохраняются. Перед новым
независимым выводом потребуется отдельный holdout, поскольку dev уже просмотрен.
Проверки диагностики: четыре новых теста (границы train/dev, обнуление блоков,
точность logit-разложения, train-диапазоны) и Ruff. Код и голова v2 сверены по SHA.

Воспроизведение в новую папку:

```powershell
.venv\Scripts\python.exe scripts/diagnose_configuration_classifier_v2.py --out research_results/classifier_v2_diagnosis_repeat
```

### Ограниченный опыт: полезность переключения и признаки схемы — 09.11.2026

Эксперимент выполнен офлайн. Реализация:
[experiment_anchor_utility.py](../scripts/experiment_anchor_utility.py),
модуль признаков/цели:
[configuration_utility.py](../src/adv_text2sql/mcp_servers/text2sql_tool/src/configuration_utility.py).
Результаты: [`classifier_anchor_utility_20261109/`](../research_results/classifier_anchor_utility_20261109/).
План, варианты, параметры, поля признаков, групповые fold и фильтр кандидатов
записаны в `experiment.json` **до fit и оценки новых вариантов**. Старые код,
модель, датасет и наблюдения не перезаписаны.

| Часть опыта | Зафиксированная реализация |
| --- | --- |
| Данные | Только 251 train-вопрос: 131 BIRD и 120 Ambrosia, прежние четыре grouped fold |
| Контроли | All-false baseline и постоянные рабочие опоры по задаче |
| Варианты | Абсолютное качество / прямая полезность × исходные входы / входы с признаками схемы |
| Общие настройки | 120 эпох, AdamW, lr=0,01, weight decay=0,01, seed=42, margin=0,15; отдельного подбора параметров нет |
| Абсолютное качество | Замороженный MiniLM + 6 счётчиков; прежняя masked BCE и 9 выходов качества профилей |
| Прямая полезность | 7 выходов альтернатив опорам; цель `quality(config) − quality(anchor)` в {−1,0,+1}; tanh и masked MSE |
| Неизвестные исходы | Цель переключения наблюдаема только при известных исходах и конфигурации, и опоры; равенства дают 0 |
| Масштабирование | Все scaler обучаются только внутри fitting-части fold, отдельно от validation |
| Проверки | Новых dev/test-оценок, API/DB-вызовов, синтетики и новых меток нет |

Семь utility-выходов — четыре альтернативы compact у BIRD и три альтернативы
14+32 у Ambrosia. Полезность опоры фиксирована в нуле. Это полезность целой
конфигурации в контексте опоры, не независимые метки фичей. Нулевые исходы
не удаляются и не превращаются в положительные; дополнительные веса редких
классов в этом ограниченном опыте не вводились.

**24 дополнительных признака** фиксированы в коде до опыта: длины question и
evidence; наличие числа, даты, кавычек; count/sum/average/extremum/comparison/time/
scope/conjunction cues; доли совпадающих слов вопроса с колонками и таблицами,
совпадений evidence с колонками; число совпавших колонок/таблиц; неоднозначные
совпадения между таблицами; доля повторяющихся имён колонок; максимальное
покрытие слов одной колонки; число совпавших числовых, временных и текстовых
колонок. Токенизация детерминированная с простыми правилами нормализации слов.

На вход экстрактора идут только question/evidence/структурные счётчики и строки
снимка `[table, column, type]`. ID БД нужен для получения снимка, но не становится
числовым/текстовым признаком. Префиксы семейств Ambrosia, SQL, эталоны и исходы
не используются в признаках. Значений строк БД и распределений в этом снимке нет.
Это простой вариант лексического связывания со схемой, не полная модель её семантики.

**Фильтр кандидатов по каждой задаче:** минимум +2 верных ответа против опоры,
положительная разность хотя бы в двух fold, ни один fold не теряет больше одного
ответа; для Ambrosia дополнительно не должны падать F1 и recall. Это заранее
заданный практический фильтр, не тест статистической значимости. Усреднение
двух бенчмарков не используется, чтобы выигрыш на одном не скрывал потерю другого.

| Подход — только train OOF | BIRD, верно / 131 | Ambrosia, верно / 120 | Ambrosia F1 | Ambrosia recall | Прошёл фильтр BIRD / Ambrosia |
| --- | ---: | ---: | ---: | ---: | --- |
| All-false baseline | 70 | 83 | 5,13% | 2,63% | Контроль |
| Постоянные рабочие опоры | **82** | 96 | 61,29% | 50,00% | Контроль |
| Абсолютное качество, исходные входы | 81 | **97** | **63,49%** | **52,63%** | Нет / нет |
| Абсолютное качество + 24 признака | 79 | 93 | 54,24% | 42,11% | Нет / нет |
| Прямая полезность, исходные входы | 74 | **97** | 59,65% | 44,74% | Нет / нет |
| Прямая полезность + 24 признака | 72 | 96 | 58,62% | 44,74% | Нет / нет |

Контроль `quality_base` в точности воспроизвёл прежние OOF 81/131 и 97/120.
Прямая utility-модель на BIRD переключается чаще и теряет восемь ответов
без исправлений; с признаками — десять. На Ambrosia её +1 верный ответ получается
из четырёх исправлений и трёх ухудшений, но TP уменьшается с 19 до 17,
поэтому recall/F1 ниже опоры. Сам факт +1 Accuracy не означает улучшение детектора.

**Решение:** ни один вариант не выдвинут на следующую валидацию.
`nominations={bird: task_anchor, ambrosia: task_anchor}`, `adopt_as_default=false`.
Сохранены 16 исследовательских fold-heads, их SHA, scaler и все 251 OOF-решение
для каждого варианта. Полная production-модель по результату этого опыта не
обучалась, новых сравнений на dev нет. API-расход — **0 токенов / $0 API**.

Этот результат отклоняет проверенные варианты при выбранной архитектуре и
настройках; он не доказывает бесполезность schema linking или utility regression
вообще. Добавление признаков одновременно увеличивает число параметров и может
ухудшать перенос при небольшом числе групп. Причину падения нельзя считать
однозначно установленной по одному ограниченному опыту.

**Дальше приоритет — данные:** аудит доступных новых train-БД и поддержка
информативных переключений контрольными повторами. Для BIRD сейчас всего четыре
train-БД, 26 различающихся вопросов и нет совместимых повторов train;
для шести Ambrosia train-точек уже обнаружена вариативность опоры. Бесконечную
настройку этих же четырёх групп и платный downstream-повтор по текущим моделям
не назначаем. Прежние dev/test не переносим в train; набор новых наблюдений
нужно зафиксировать отдельным протоколом перед платным сбором.

Проверки: **10 новых тестов** знака/контекста utility-целей, unknown-масок,
нулевого градиента другой задачи, признаков, scaler, границы train/dev и фильтра
Accuracy/F1/recall; Ruff пройден. Воспроизведение в новую папку:

```powershell
.venv\Scripts\python.exe scripts/experiment_anchor_utility.py --out research_results/classifier_anchor_utility_repeat
```

### Последовательность реализации и текущий статус

Пункты 1–5 выполнены для ограниченного каталога этой серии. Пункт 6 проверен
по сохранённым ответам; свежего downstream-прогона и независимого holdout не было.

1. **Расширить каталог и ограничения отдельной версией.** У v1 отсутствует FEAT_7,
   а лимит — три фичи. Новая версия должна допускать текущую пятифичевую опору BIRD
   и зависимость FEAT_7 → FEAT_2. Старые checkpoints должны оставаться читаемыми.
2. **Зафиксировать ограниченный каталог измеряемых конфигураций.** Использовать
   результаты семантического анализа и статических экспериментов; не возвращаться
   к перебору всех сочетаний. Разделять структурные зависимости и гипотезы о пользе.
3. **Проверить совместимость архивных наблюдений.** Сопоставлять вопрос, схему,
   модель/версию, параметры генерации, промпты, эффективные флаги и evaluator.
   Учитывать расхождение объявленного и фактического лимита ответа, обнаруженное
   выше; совпадения имени модели недостаточно для автоматического переноса.
4. **Подготовить новые train-метки.** Сохранять конфигурацию-контекст и разность
   сопоставимых исходов. Не раздавать эффект всей комбинации отдельным фичам.
   Неизвестные цели остаются `null` и исключаются маской из loss. Для сравнения
   моделей на dev нужны совместимые dev-наблюдения, отдельные от train.
5. **Переобучить и выбрать по dev.** Начать с замороженного MiniLM, структурных
   признаков и небольшой обучаемой части. Сравнить с v1, all-false и фиксированным
   профилем своей задачи. Учесть сочетания, а не только независимые положительные метки.
6. **Измерить downstream-качество и стоимость.** EX для BIRD; detection Accuracy,
   F1/recall для Ambrosia; токены/вызовы/время для обоих. Положительный результат
   обучения головы не равен улучшению Text-to-SQL. Для независимого финального
   вывода потребуется новый holdout: прежний test и full уже просмотрены.

Синтетика не требуется для этого первого этапа. Не переносим dev/test-вопросы
в train и не используем эталонный SQL как вход классификатора. Полная схема
сейчас не кодируется MiniLM; шесть счётчиков не заменяют семантику схемы.
