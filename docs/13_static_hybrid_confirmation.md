## Цель и условия

Выбрать лучший наблюдаемый статический набор из ограниченного меню, проверить
устойчивость и затем обновлять supervision классификатора. Глобальный максимум
по всем допустимым FEAT-комбинациям этот эксперимент не доказывает.

| Условие | Зафиксированное правило |
| --- | --- |
| Модель | Прямой DeepSeek из `.env.deepseek`, та же объявленная версия, что в исходных опытах |
| Флаги | Явная маска всех 36 флагов; baseline — все false |
| Вход BIRD | Те же question/evidence, schema и SQL-generator; temperature=0, thinking disabled |
| Train | BIRD 131, Ambrosia 120 при явном `exclude_mismatches` |
| Dev | BIRD 55, Ambrosia 46 |
| Исключения | 16 несогласованных вопросов Ambrosia, перечислены в audit и manifest; исходный датасет 227 не редактируется |
| Защита схем | `require_all` по умолчанию блокирует запуск; live-каталог должен совпасть с snapshot до платных вызовов |
| Ошибки вывода | Невалидный финальный ответ → error и checkpoint, без скрытой повторной генерации; FEAT_17 остаётся исследуемым механизмом |
| Рейтинг | Равное среднее Accuracy BIRD/Ambrosia; отдельно показатели каждого benchmark и F1/FP Ambrosia |
| Точные равенства | Меньше записанных токенов, затем меньше флагов, затем имя |
| Исторические ответы | Только справочный материал; в новом рейтинге отсутствуют |
| Изоляция | Full/test scope отсутствуют; новые данные классификатора в этом этапе не создаются |

Фиксируются исходники, masks/cohorts, Python и версии ключевых пакетов. Ротация
имени API-модели на стороне провайдера не исключена: локальный model_version —
объявленная идентичность, а не проверяемый хеш серверных весов.

## Отбор, повторы и итог

1. На train выполняются 15 масок по одному разу: это разведочный screening.
2. Команда `--freeze-finalists` выбирает лидеров train по macro, BIRD и Ambrosia.
   Совпавшие имена объединяются; если остался один кандидат, добавляется второй
   по macro. Получается 2–3 новых кандидата плюс baseline и H.
3. Имена финалистов, protocol hash и хеши исходных screening-ответов фиксируются
   до dev. Повторная команда идемпотентна; изменение train-ответов блокирует reuse.
4. Для выбранных кандидатов и обоих контролей дополняются train-повторы 2 и 3.
   Неудачный повтор не заменяется более удачным; checkpoints не перезаписываются.
5. Все те же 4–5 конфигураций выполняются на dev по три раза. Порядок конфигураций
   между повторами меняется; вопросы внутри cohort сохраняют исходный порядок.
6. Итоговая таблица показывает среднее/диапазон, парные исправлено/испорчено,
   Δ к H по каждому повтору, F1, ошибки, токены и описательный bootstrap-интервал.

Повторы не являются новыми независимыми вопросами. Bootstrap сохраняет пары
конфигураций, пересэмплирует блоки повторов и кластеры БД; при малом числе БД
интервал остаётся описательным, без поправки на множественные сравнения. Он не
подменяет анализ ошибок или независимую итоговую оценку.

Лучший средний dev-score называется **лучшим наблюдаемым**. Если преимущество
над H меняет знак между повторами или интервал включает ноль, устойчивое
превосходство не заявляем. Допустимый результат — сохранить H как контроль и
зафиксировать кандидата с неопределённым преимуществом. По отдельности сохраняем
лидеров BIRD/Ambrosia. Dev используется для выбора; прежний просмотренный test
не становится независимым из-за нового названия папки.

### Не приписывать весь прирост Ambrosia FEAT_2

Сопоставлены валидные taxonomy-ответы из raw_responses: у H+2 все 70/70 запросов
к детектору дословно совпадают с H. Вердикт поменялся для ID 19, 60, 269, во всех
трёх случаях true → false. Один пустой ответ прерванной попытки H явно исключён
из этого сравнения как не содержащий вердикт; из H+2 исключений нет.

Следовательно, наблюдаемые +2 Ambrosia не доказывают прямую пользу статистик
для детекции: изменились ответы на одинаковые сообщения, а также исчезла одна
итоговая ошибка генерации. На BIRD сравнение фиксирует положительный net +4,
но одного повтора недостаточно для устойчивого вывода. В предыдущем v2 на этих
train ID отрыв H+2 от свежего H был +8: вариативность уже заметна.

### Найденные ограничения реализации

## Повторный сбой API/null-ответов — 03.11.2026

После возобновления hybrid_plus_2__r3/Ambrosia формально завершён, очередь
перешла к statistics_compact__r3/BIRD. На этом запуске в autogen_ext/models/openai/
_openai_client.py:712 возник AttributeError: 'NoneType' object has no attribute
'usage'. Клиент получил result=None и попытался обратиться к result.usage;
это не ошибка SQL или отсутствие поля usage у обычного непустого ответа.
В тех же логах есть HTTP 503 Service is too busy. Причину null-ответа на стороне
провайдера по локальным логам установить нельзя.

RecordingClient ловит Exception и поднимает ProviderUnavailable только после
трёх последовательных сбоев; успешный вызов обнуляет счётчик. Одиночные 503 и
AttributeError поэтому попадают в широкие catch генератора/детектора: результат
может быть сохранён как model error или использован fallback детекции. Запись
consecutive_api_errors=0 позднее не доказывает отсутствие таких сбоев в запуске.
