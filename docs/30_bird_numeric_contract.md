# Числовой контракт BIRD evaluator

16.11.2026. Реализован общий контракт для базового BIRD evaluator, исследовательского
`Session.score`, его preflight и ручного пересчёта статического pipeline.

## Что требует официальный BIRD

Проверены два первичных источника:

- [BIRD Mini-Dev: calculate_ex](https://github.com/bird-bench/mini_dev/blob/main/evaluation/evaluation_ex.py).
- [Исходный BIRD: execute_sql](https://github.com/AlibabaResearch/DAMO-ConvAI/blob/main/bird/llm/src/evaluation.py).

Оба сравнивают точные множества строк: порядок строк и число одинаковых дубликатов не учитываются,
порядок колонок и сами значения учитываются. Числового допуска и округления в этих функциях нет.
Это проверка опубликованного кода по состоянию на указанную дату, не утверждение о неизменности
веток main в будущем. Прямое сравнение с leaderboard также требует исходных данных и протокола BIRD;
тот же оператор сравнения на перенесённых базах PostgreSQL сам по себе этого не обеспечивает.

## Реализация

| Компонент | Контракт | Влияет на EX / метки |
| --- | --- | --- |
| `bird-exact-set-v1` | Точное равенство множеств без округления, приведения `Decimal` к `float` и допуска | **Да: единственный источник score** |
| `bird-postgres-serial-repeatable-read-v1` | В read-only транзакции до SELECT включаются REPEATABLE READ и локальное `max_parallel_workers_per_gather=0`; прежний timeout 30 секунд сохраняется | Меняет только условия выполнения PostgreSQL, не правило сравнения |
| `postgres-numeric-warning-v1` | Отдельная диагностическая пометка о близких числах разной точности | **Нет: не начисляет EX и не создаёт положительные метки** |

Общий код: [bird_results.py](../src/adv_text2sql/bird_results.py). Оба пути оценки используют
его одинаково и сохраняют `bird_comparison` с версиями правил, точным результатом и диагностикой.
Настройки PostgreSQL действуют только внутри транзакции оценки; генерация SQL, серверные
настройки, фичи и промпты не менялись. При отказе настройки транзакции выполнение останавливается
без модельной метки. Последовательное исполнение может быть медленнее параллельного;
при timeout отрицательный ответ модели не сохраняется.

Диагностика использует OID типа результата: для `REAL` — относительную границу 2⁻²³,
для `DOUBLE PRECISION` — 2⁻⁴⁸ (16 машинных epsilon). Если OID неизвестен, применяется более строгая
граница `DOUBLE`, а не предположение о `REAL`. Абсолютного допуска около нуля нет.
Это собственные фиксированные границы предупреждения, **не правила BIRD и не доказательство
семантической правильности SQL**. Целые значения, две величины `Decimal`, строки, NULL,
массивы/JSON и бесконечности не получают приблизительного сравнения.
Используется взаимно однозначное сопоставление строк при сохранении мощности множества,
а не округление ключей или жадный поиск. При более чем 100 000 пар диагностическое сравнение
может вернуть `null`; точный score от этого не меняется.

## Проверка на PostgreSQL

| Вопрос | Исторический SQL, новый evaluator | Свежий сохранённый SQL, новый evaluator | Вывод |
| --- | ---: | ---: | --- |
| 1473 | **1** | **1** | При последовательном AVG все три варианта вернули одинаковое число в трёх повторах |
| 34 | **1** | **0**, `numeric_precision_warning=true` | Отношение 139/689 совпадает по смыслу, но `REAL` и `NUMERIC` различаются; официальный точный контракт не даёт начислить балл |

Проверены реальные `Session.score`, типы результатов и фактические настройки транзакций
(`read_only=on`, `repeatable read`, parallel workers=0). Результаты и хеши проверенной версии
runtime сохранены в `research_results/bird_numeric_contract_20261116/runtime_check.json`.
Проверка ограничена двумя вопросами, **не является новой полной метрикой BIRD**.
LLM-вызовов — **0**. Исторические JSON, checkpoint, scores и бюджеты не перезаписывались.

Для №34 остаётся отдельная задача переноса SQLite → PostgreSQL: проверить соответствие
числовых типов и вычислений на оригинальных SQLite-базах. Нельзя решать её незаметным
ослаблением EX или специальной обработкой номера вопроса. Исходные SQLite-базы в эту
проверку не входили; прежний скалярный SQLite-контроль не заменяет такую проверку.

## Тесты и повторный пересчёт

**116 тестов прошли**, включая 225 сопоставлений результатов реальных SQLite-запросов с
точным оператором официальной EX, большие целые, `Decimal`, близкие неверные ответы,
NULL/строки, структуру строк, дубликаты, сопоставление без жадных коллизий, реальные базовый
и исследовательский evaluator, отсутствие ложной положительной метки классификатора,
ошибки настройки защиты, checkpoint и full-pipeline preflight. Ruff прошёл.

Старый протокол r2 оставлен неизменным. Новые исходники закономерно не проходят его проверку
хешей: продолжать его с подменённым SHA нельзя. Для ручного пересчёта **исторических сохранённых
ответов** подготовлен отдельный каталог и новый fingerprint:

```bash
bash local/run_static_pipeline_regression.sh --prepare --output research_results/static_pipeline_audit_numeric_20261116
bash local/run_static_pipeline_regression.sh --action reevaluate --benchmark bird --output research_results/static_pipeline_audit_numeric_20261116
```

Первая команда офлайн; вторая требует SSH/PostgreSQL, но не вызывает LLM. Полный пересчёт
впоследствии завершён вручную — итог ниже. Столбец свежей генерации нового протокола остаётся пустым;
результаты свежих ответов r2 не импортируются под новым кодом. Для их полной переоценки
потребуется отдельный явно обозначенный контроль сохранённых SQL, без необходимости
заново генерировать ответы. Ambrosia этим числовым контрактом не переоценивается.

## Восстановление соединения при ручной переоценке

После 164 сохранённых оценок пересчёт остановился при исполнении SQL №736 (`superhero`),
а повторный запуск — уже на чтении схемы `california_schools`. Прежний launcher проверяет
только открытие порта 5444; это не проверка работоспособности PostgreSQL.
При отдельной диагностике SSH-сервер достиг порта PostgreSQL, обе БД ответили на `SELECT 1`,
а сохранённый SQL №736 исполнился. Это подтверждает доступность в момент диагностики,
но не устанавливает точную причину прежнего разрыва или таймаута.

Добавлен отдельный supervisor, без изменения исходников замороженного evaluator:

```bash
bash local/resume_static_reevaluation.sh --output research_results/static_pipeline_audit_numeric_20261116
```

Он проверяет прежний manifest/checkpoint, выполняет read-only `SELECT 1` для всех восьми БД
и запускает **исходный** `static_pipeline_regression.py --action reevaluate`. При подтверждённой
потере доступа восстанавливает только свой SSH-процесс и продолжает по checkpoint, максимум
два автоматических перезапуска. Если после ошибки worker доступ к БД исправен, ошибки SQL,
схемы и statement timeout не маскируются слепыми повторениями. При SQLSTATE `57014`, отказе
аутентификации, отсутствии БД или прав автоматического повтора нет. Чужой туннель не убивается:
если его порт занят, но БД недоступна, supervisor останавливается с явным сообщением.

В момент подготовки сохранены **164/241** оценок; осталось **77**, начиная с №736.
Файл оценок проверен побайтово и не изменялся. Новые launcher и supervisor не меняют список
исходников старого manifest, поэтому новый SHA или повторный `--prepare` не нужен. Собственный
SHA supervisor записывается отдельно в `connection_resume.json`; подробности SSH остаются
в игнорируемом `connection_resume_tunnel.log`. Платных вызовов этот запуск не делает.

Офлайн-проверка доступна с `--dry-run`. **38 тестов** supervisor, старого runner и числового
контракта прошли; дополнительно проверены Ruff, синтаксис Bash и прежний fingerprint.

## Итог полного пересчёта исторических ответов

Пересчёт **241/241 BIRD** завершён. Все записи `scored`, ошибок эталонов и исполнения
сохранённых ответов нет. Текущие исходники, модель и checkpoint соответствуют manifest.

| Условие оценки одних и тех же исторических SQL | Правильно | EX |
| --- | ---: | ---: |
| Историческая оценка | 132/241 | 54,77% |
| Первая переоценка, до стабилизации PostgreSQL | 131/241 | 54,36% |
| Текущий точный контракт и последовательное выполнение | **133/241** | **55,19%** |

Относительно исторической оценки ухудшений нет, `1476` изменился с 0 на 1.
Относительно первой переоценки с 0 на 1 изменились `1473` и `1476`.
Для `1473` влияние параллельного AVG подтверждено отдельным контролем. В `1476` есть SUM
и разные формы фильтра года; причиной изменения оценки без отдельной проверки его результатов
нельзя уверенно объявлять только параллелизм.

Диагностические предупреждения о числовой близости сохранены у **12 ответов**: `116, 282, 416,
598, 701, 818, 835, 760, 775, 834, 1359, 1471`. Все они сохранили точный score=0;
предупреждение не доказывает правильность смысла SQL и не добавляет баллы.
Исторический SQL №34 по-прежнему имеет score=1; его свежий вариант с NUMERIC в этот
пересчёт не входит и ранее при точном сравнении получил 0.

Продолжение с 164 до 241 результатов завершилось с первой попытки supervisor, без
автоматического перезапуска. В новом каталоге нет LLM-ledger: **вызовов LLM и новых токенов — 0**.
Проверки полноты, точного соответствия scores контракту и хеши источников записаны отдельно
в `research_results/static_pipeline_audit_numeric_20261116/completion_review.json`.

Это **исправление и проверка оценки**, не улучшение генератора. Свежий прогон r2 (128/241,
53,11%) целиком новым контрактом ещё не переоценивался; сравнивать его напрямую с 55,19%
как эксперимент на одном evaluator нельзя. Ambrosia в этом запуске не проверялась.
Для коммита исправлений контроль исторической опоры завершён; последние исходники, новые
тесты и launcher необходимо включить в staging.
