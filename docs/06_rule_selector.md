# Phase 1 — селектор конфигураций по правилам

**28.10.2026: селектор реализован, офлайн-проверка завершена. Преимущество
динамического выбора над статическим гибридом на test не подтверждено.**
Новых вызовов LLM, подключений к БД и платных прогонов не было.

## Что реализовано

| Компонент | Файл / поведение |
| --- | --- |
| Правила | [feature_selector.py](../src/adv_text2sql/mcp_servers/text2sql_tool/src/feature_selector.py): вопрос → конфигурация, полный набор флагов и причины |
| Интеграция генератора | [selective_generator.py](../src/adv_text2sql/mcp_servers/text2sql_tool/src/selective_generator.py): async `build()` / `query()`, изолированные флаги |
| Оценка | [evaluate_rule_selector.py](../scripts/evaluate_rule_selector.py): фиксация по dev и отдельный replay test |
| Результаты | [comparison.md](../research_results/rule_selector_deepseek_20261028/comparison.md), полный [report.json](../research_results/rule_selector_deepseek_20261028/report.json) |
| Политика | [selection.json](../research_results/rule_selector_deepseek_20261028/selection.json): выбранные правила, модель, ID train/dev, хеши данных и кода |
| Подробности | `development.json` — все кандидаты; `train_cv.json` — диагностика внутри train; `decisions.jsonl` — выбор и причины по 468 вопросам |

Селектор выбирает только между проверенными **35** (`economical`) и **14+32+35**
(`hybrid`). Остальные флаги false, включая 17 и 33. Инфраструктурные настройки
не превращаются в предсказываемые фичи. Классическая проверка неоднозначности
в economical сохранена, как в исходном эксперименте; её отключение было бы
отдельной конфигурацией, для которой сохранённых наблюдений пока нет.

Входы: question, evidence, schema_stats. Правила используют текст вопроса и
число таблиц/колонок; evidence передаётся генератору, но не даёт дополнительных
сигналов правилам. Значения в кавычках исключаются из поиска маркеров.
Идентификаторы БД, benchmark, gold SQL, labels, split и ответы модели в селектор
не передаются. Неизвестные поля входа отклоняются.

## Протокол выбора

Каталог из шести политик задан в коде: два статических контроля, маркеры
неоднозначности, их сочетание со сложностью SQL, с размером схемы и строгий
порог сигналов. Используются кванторы, смешанные and/or, присоединение
модификатора, местоимения и расплывчатые сравнения; сложность — агрегации,
ранжирование, группировка, сравнения и исключения.

Правила не обучаются. На train проверено их поведение, на dev выбрана политика
с максимальной средней Accuracy двух задач. При равенстве используется меньшая
оценка токенов по средним исходных прогонов, затем порядок каталога. Test не
участвует в выборе. Политика и код зафиксированы перед отдельным replay test;
изменение кода или данных требует нового эксперимента.

Выбрана **strong_signals**: hybrid при двух и более сигналах неоднозначности
или двух и более сигналах сложности SQL; иначе economical. Статистики схемы
этой выбранной политикой не используются. Четыре fold внутри train — только
диагностика фиксированных правил, а не обучение четырёх моделей.

| Политика | Train: средняя Accuracy | Dev: средняя Accuracy | Dev: оценка токенов |
| --- | ---: | ---: | ---: |
| Всегда economical | 61,66% | 58,77% | 166 468 |
| Всегда hybrid | 67,58% | 58,22% | 335 577 |
| ambiguity | 66,11% | 58,60% | 248 313 |
| ambiguity_or_complexity | 66,11% | 59,51% | 263 031 |
| ambiguity_or_large_schema | 66,49% | 55,87% | 273 544 |
| **strong_signals** | **62,41%** | **59,51%** | **214 331** |

## Отложенные результаты

Сравниваются одинаковые test ID: BIRD 55 вопросов / 2 БД, Ambrosia 45 / 14 БД.

| Подход | BIRD: верно | BIRD Accuracy | Ambrosia: верно | Ambrosia Accuracy | Ambrosia F1 |
| --- | ---: | ---: | ---: | ---: | ---: |
| Всегда economical: 35 | 19/55 | 34,55% | 34/45 | 75,56% | 15,38% |
| Всегда hybrid: 14+32+35 | **22/55** | **40,00%** | **39/45** | **86,67%** | **66,67%** |
| Селектор strong_signals | 18/55 | 32,73% | 33/45 | 73,33% | 0,00% |

На test селектор направил в hybrid 12/55 вопросов BIRD и 2/45 Ambrosia.
Относительно статического hybrid потеряны четыре правильных ответа BIRD и
шесть правильных классификаций Ambrosia, новых правильных ответов нет.
Правила слишком редко включают таксономический детектор. Небольшое преимущество
по средней Accuracy на dev не перенеслось на другие БД test.

Токены в отчёте — **приближение по средним полных исходных прогонов**, включая
probe/build. Точные затраты выбранных вопросов неизвестны. Это не измеренная
экономия и не основание объявлять селектор эффективнее.

Test остаётся **ретроспективным**: статические конфигурации ранее выбирались
с использованием этих наборов. Совпадения с примерами промптов отмечены в
`report.json`. Ambrosia измеряет детекцию неоднозначности, а не EX SQL.
Независимый финальный test пока отсутствует. По результатам test правила
не подстраивались, выбранный кандидат не заменялся другим задним числом.

## Воспроизведение без оплаты

```powershell
.venv\Scripts\python.exe scripts/evaluate_rule_selector.py prepare
.venv\Scripts\python.exe scripts/evaluate_rule_selector.py evaluate
```

Первая команда использует train/dev и сохраняет выбор. Вторая читает уже
зафиксированную политику и оценивает все части. Повтор допускается только с
идентичными артефактами. Для новой версии правил задайте новый каталог `--out`.
Исходные данные Phase 0.2 и результаты LLM-прогонов не переписываются.

## Интеграция и ручной live-запуск

`SelectiveText2SQLGenerator` готовит TSV-схему один раз и использует её для обеих
конфигураций. Каждая конфигурация имеет свой модуль с собственными флагами;
переключения глобальных env-переменных между вопросами нет. Конкурентные вызовы
проверены с подставным клиентом, без API и PostgreSQL. Результат `query()` содержит
`feature_selection` с конфигурацией, фичами и причинами. Для приложения нужно
передать селектор, загруженный через `RuleBasedFeatureSelector.from_file()`.

В существующий launcher добавлены `--configuration selector` и
`--selector-policy`. Политика привязана к исходной модели, версии и endpoint;
для другой модели нужна отдельная оценка. Metadata сохраняет кандидатов и хеш
политики, а `selector_decisions.jsonl` — выбор на каждом запросе.

Проверка параметров без SSH, БД и LLM:

```powershell
.venv\Scripts\python.exe scripts/run_openrouter_baseline.py --configuration selector --selector-policy research_results/rule_selector_deepseek_20261028/selection.json --env-file .env.deepseek --model deepseek-flash --benchmark both --evaluation-policy strict --output research_results/rule_selector_deepseek_live_20261028 --dry-run
```

Если потребуется отдельная техническая live-проверка, запускать вручную:

```powershell
bash local/run_openrouter_baseline.sh --configuration selector --selector-policy research_results/rule_selector_deepseek_20261028/selection.json --env-file .env.deepseek --model deepseek-flash --benchmark both --evaluation-policy strict --output research_results/rule_selector_deepseek_live_20261028
```

Эта команда платная, **не запускалась**. Полный платный прогон текущих правил
пока не рекомендуется: офлайн-оценка уже показала снижение качества.

## Следующий шаг

Сохранить статический 14+32+35 как основную конфигурацию. Phase 1 реализована
технически, критерий Roadmap «динамический выбор лучше статического» не выполнен.
Следующий исследовательский шаг — обучаемый выбор конфигураций с групповой
валидацией и анализом ошибок на train/dev. Данных с различием качества всего
75, из них 42 в train; устойчивый прирост не гарантирован.

Выбор двух конфигураций ещё не является независимым multilabel-выбором всех
фичей. Для такого Phase 2 потребуются корректные наблюдения полезности отдельных
механизмов/групп и учёт зависимостей. Новые версии нужно оценивать с явным учётом
того, что текущий test уже просмотрен, затем проверить на новых БД/вопросах.

Проверки реализации: 66 офлайн-тестов, Ruff, проверка bundle Phase 0.2,
реальные offline prepare/evaluate и dry-run launcher на обоих бенчмарках.
