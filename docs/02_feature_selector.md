## Порядок испытаний

1. Разделить данные по модели/конфигурации и зафиксировать question IDs,
   hash схем/промптов, evaluator и реальные активные зависимости.
2. Исправить builder: отличать корректность от полезности фичи, пропуски от
   отрицательных меток, восстановить ссылку на реальный best hybrid.
3. Задать utility = feature_correct − baseline_correct (−1/0/+1) для анализа;
   отдельно хранить исходные score, стоимость и mask наблюдаемых меток.
4. Разделять train/dev/test по БД и семействам вопросов. Small является
   подмножеством large, а не дополнительными независимыми данными.
5. Проверить зависимости и эффективные флаги: №3/4/7 требуют №2;
   №33 требует №32; №36 требует №15. Текущая серия DeepSeek по запросу
   пользователя включает строго один флаг и сравнивает его только с all-false
   baseline, как Mistral. Неактивный без зависимости механизм отмечать отдельно;
   не считать его случайный прирост доказанной полезностью. Инфраструктуру
   не предсказывать по вопросу.
6. Начать с простого selector; сравнить с зафиксированными статическими
   конфигурациями на отложенной части. Для multilabel нужны новые корректные
   абляции, а не только два полных GPT-прогона.

### Как строить гибрид

1. Получить компактный **статический гибрид**: представление схемы, опциональные
   статистики/правила и отдельный модуль неоднозначности. Совместное качество
   проверяется экспериментом; приросты одиночных флагов не складываются.
2. Подготовить данные селектора из ответов DeepSeek: по вопросу хранить baseline,
   конфигурацию, правильность, generation error, стоимость, активность механизма
   и наблюдаемую разность правильности. Для Ambrosia дополнительно хранить
   эталонный класс и последствия ложных срабатываний; для BIRD — SQL score.
   Не смешивать эти две задачи в одну неразличимую метку качества.
3. Начать с выбора между небольшим числом **проверенных конфигураций**. Входы:
   вопрос, доступные признаки схемы/БД, дешёвые признаки сложности. Эталонный SQL
   и правильность ответов используются только при обучении и оценке.
4. Проверить простой rule-based selector и обучаемый router против лучшего
   статического гибрида по downstream качеству и стоимости. Сам селектор не
   должен предварительно получать ответы всех конфигураций на каждом вопросе:
   это уже другой, более дорогой эксперимент с reranking.
5. Затем обучать multilabel для небольшого числа совместимых групп, если данных
   достаточно. Формат схемы — выбор одной альтернативы; статистики, строгие
   правила, связи, детектор — отдельные решения с явными ограничениями.
   Инфраструктурные и неактивные флаги исключить из предсказываемых меток.

Текущие 241/227 уже многократно использовались для выбора фичей. Ретроспективный
split по БД/семействам полезен для разработки, но не превращает эту выборку в
независимый финальный тест. Для подтверждения обобщения нужен новый отложенный
набор вопросов/БД. В BIRD здесь только восемь БД; оценку router следует проводить
с группировкой по БД, а в Ambrosia также учитывать близкие шаблоны вопросов.

Случайные отличия одинаковых промптов не дают достоверных меток причинной пользы.
Селектор обучается предсказывать наблюдаемую полезность при заданном протоколе;
его преимущество проверяется на отложенных данных относительно лучшей фиксированной
конфигурации. Сам классификатор пока не обучен; новые комбинации не запускались.

Accuracy не изменилась: BIRD 117/241, Ambrosia 182/227; F1 Ambrosia 58,72% вместо

Фиксируем **14+32+35** как основную опору и **35** как экономичный контроль.
Ответы варианта с 1 сохраняем как дополнительные наблюдения. Следующий этап —

необязательный промежуточный эксперимент; глобальный перебор сочетаний не требуется.
