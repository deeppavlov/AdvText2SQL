## Почему исходные показатели Ambrosia требуют оговорки

Найдено **40 невалидных сохранённых ответов** среди 12 завершённых конфигураций
(два core-набора, повтор H и девять additions): 39 ответов Ambrosia на 8 разных
вопросах и один BIRD с двумя SQL-операторами. Все 8 проблемных Ambrosia-вопросов
относятся к базе с несоответствующей схемой.

В исходном генераторе comments-only ответ мог очищаться до пустой строки и всё же
возвращаться со status=success при выключенной FEAT_16. Launcher останавливался.
При ручном повторе модель иногда давала непустой текст отказа, который проходил
как success. Оценщик Ambrosia классифицировал его как not ambiguous и мог засчитать
true negative. Поэтому одного правила «строка error всегда неверна» недостаточно.

Сохранённые ответы пересчитаны **отдельно**, без их перегенерации и без изменения
исходных report.json. Невалидный ответ теперь трактуется как error, а не ambiguous.

| --- | ---: | ---: |
| Свежий H | 75,00% | 73,53% |
| H+2 | 75,74% | 72,79% |
| H+25 | 75,74% | 73,53% |
| H+30 | 75,74% | 75,00% |

Нельзя сравнивать новую колонку с исходной колонкой другого кандидата. Полная
таблица находится в [аудите качества](../research_results/deepseek_combinations_large_20261026/quality_audit_20261029/comparison.md).

## Проверка соответствия вопросов схемам

Проверены **все 468 вопросов**, а не только train. Схемы восстановлены из сохранённых
TSV-промптов канонического FEAT_35, использованных также исходным builder датасета.
Для однозначных вопросов разбирается эталонный SQL, для ambiguous — все сохранённые
SQL-интерпретации. Учитываются SQLite backticks, области видимости подзапросов,
CTE, регистр имён и SQLite double-quoted literals в позициях значений.

| Benchmark | Проверено | Ссылки SQL согласованы со схемой | Несоответствие | Требует ручного разбора |
| --- | ---: | ---: | ---: | ---: |
| BIRD | 241 | 241 | 0 | 0 |
| Ambrosia | 227 | 211 | **16** | 0 |

Все 16 несоответствий — `vague_2cols_location`, ID:
`267, 271, 275, 276, 277, 278, 279, 281, 298, 299, 300, 301, 302, 303, 304, 305`.
SQL требуют Properties/Transactions/Clients/ClientProperties либо Office/Job_Posting/Department.
В сохранённой схеме есть Students/Teachers/Classes/Departments/Facilities. Имена
Department и Departments не считаются одной таблицей автоматически.

Несоответствие уже присутствовало в исторических промптах; это не дефект,
созданный FEAT_25. Локального оригинального архива/SQLite/DDL для восстановления
базы в проекте не найдено. `unpack.sh` использует basename и пропускает совпавшие
каталоги; это потенциальный риск потери различий между вариантами, но доказательств,
что именно так возникла текущая проблема, без исходных архивов нет.

Это статическая проверка ссылок относительно **сохранённых** схем, а не доказательство
полной семантической корректности вопросов или текущего содержимого PostgreSQL.
При проверке локальный SSH-порт был закрыт. Новая версия перед платной генерацией
дополнительно сверяет реальный каталог с зафиксированной схемой.

## Что исправлено в новой версии

Подготовлены отдельные `guarded_hybrid_search.py` / `guarded_hybrid_runtime.py` и
launcher `local/run_guarded_hybrid_search.ps1`. Это **v3**, старый v2 не изменяется.

- Пустой SQL, одни комментарии, текст отказа, неизвестный status, несколько операторов
  и не-query ответ превращаются в `error`, записываются в checkpoint и diagnostics.
  Обработка идёт к следующему вопросу без скрытой повторной генерации.
- Проверка формы ответа не подменяет FEAT_16: синтаксическая валидация и исполнение
  SQL остаются отдельными этапами. Правильная форма не означает правильный SQL.
- Транспортный/бюджетный сбой по-прежнему останавливает очередь. Пустой/нетекстовый
  ответ самого API сохраняет защитную остановку провайдера; он отличается от SQL,
  ставшего пустым после очистки комментария.
- Известные несоответствия блокируют запуск до платного probe. По умолчанию
  `require_all`; автоматического исключения вопросов нет.
- Перед любым новым платным case выполняется read-only сверка реальных имён/типов
  таблиц и колонок со snapshot. Изменение каталога блокирует запуск и требует аудита.
- Эталонный SQL используется только в офлайн-аудите. В LLM-промпты и запрос
  исправления он не поступает. Реальные каталоги проверяются без исполнения gold.

Проверка v3 с исходной выборкой сейчас закономерно блокируется:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File local/run_guarded_hybrid_search.ps1 --dry-run
```

Для работы с явно обозначенной выборкой без 16 несоответствий (только проверка):

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File local/run_guarded_hybrid_search.ps1 --schema-policy exclude_mismatches --cases baseline_control hybrid_control_repeat hybrid_plus_2 --dry-run
```

Убрать `--dry-run` — ручной платный запуск **новых** baseline, H и H+2 на 131/120,
после live-проверки схемы. Это новая версия эксперимента, а не продолжение старого
checkpoint. Порядок явно заданных `--cases` сохраняется. Никаких новых платных
прогонов в рамках исправлений не выполнялось.

Если нужно сохранить все 227 вопросов, требуется исходный архив Ambrosia и корректное
сопоставление вариантов БД с db_id; затем восстановление БД и повторный аудит.
Нельзя выдумывать DDL/данные по эталонным SQL либо просто менять db_id на похожую базу.

Воспроизведение проверки и пересчёта без API/SQL:

```powershell
.venv\Scripts\python.exe scripts/audit_question_schemas.py
```
